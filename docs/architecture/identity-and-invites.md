# People, identity and invites

Ledgerly has to work with people who never sign up: employers, friends you lend to, a new housemate who hasn't joined yet. This page explains how one real human stays one **person**, from the first time someone types their phone number until they sign up, and after.

## Building blocks

- **Person** (`persons`): someone who can owe or be owed. `userId` is empty for placeholders.
- **Identity** (`identities`): an email or phone number that belongs to a person. The `key` column is unique, so one email or phone number can only ever belong to one person.
- **Member** (`members`): a person inside a group, with that group's display name for them. Its `status` says whether the person has **joined** the group: `placeholder` (not joined, with or without an account), `active` (joined) or `left` (joined, then moved out).

A person's contact details live only in `identities`. Group-specific names live only in `members.displayName`. Nothing else stores them. One exception: an employer group's billing addresses (`GroupSettings.recipients`) are invoice settings the worker typed, not identities, and they are never used to recognise or link a person.

## Normalising identities

Every email or phone number goes through `normalizeEmail()` or `normalizePhone()` (`packages/core/src/identity/normalize.ts`) before any lookup, and `identityKey()` builds the key from the result. Invalid input throws a `RangeError` whose message never repeats the input, and the calling route turns it into `VALIDATION_FAILED`:

| Type | Rule | Example |
| --- | --- | --- |
| email | Trim and lowercase. Dots and `+tags` are kept. | ` Sam@Example.com ` → `email:sam@example.com` |
| phone | Parse with `libphonenumber-js`, using the country from the group's `region` as the default (the group the person is being added to; `AU-NSW` → `AU`); reject numbers that `libphonenumber-js` (min metadata) calls invalid, in national or E.164 form, and numbers with an extension; format as E.164 | `0412 345 678` (AU) → `phone:+61412345678` |

## First login (bootstrap)

`identity POST /bootstrap` runs on every login and is idempotent:

1. If a profile already exists for this user, skip to step 3, so an interrupted claim always gets finished.
2. Otherwise, create the personal group's team and add the user to it ("already exists" counts as done). Like every team membership, it has no team role, never `owner`, so the user can't manage the team from the client. Then, in one database transaction:
   - Find or create the user's **person**. If one of the user's verified emails or phones matches an identity row that points at a placeholder, reuse (adopt) that person. Placeholder identity rows are never `verified` themselves, so match on the key, not the flag. Set the person's `userId` and `claimedAt` (now), clear its `orphanedAt` with a fresh `rev` (the row becomes readable to the user), and delete the placeholder's identities whose key the user hasn't verified ([only verified keys move](#only-verified-keys-move)): the verified keys come from bootstrap's own read of the user, through the same `verifiedIdentities()` as Claim step 1. After staging, bootstrap reads the stored row again, and answers `CONFLICT` (try again) if it's no longer a placeholder, as when another user adopted it or a merge marked it first.
   - Create the **profile** (row ID = user ID) with defaults: timezone from the browser, region and currency from the timezone. An Australian time zone gives its state (`Australia/Perth` → `AU-WA`); any other gives `AU-NSW`. The currency is `AUD`. The user can change all of them in their profile.
   - Create the **personal group** and the user's `admin` member row.

   The team comes first so that no saved row names a team that doesn't exist. An interrupted bootstrap can leave a team with no group row, which grants nothing.
3. Run **Claim** for any verified identities.

## Adding someone to a group

`groups POST /groups/{id}/members` with `{ displayName, email?, phone? }` (and an employer or pair group's counterpart at `POST /groups`, the same way):

1. Normalise the email and phone.
2. Look up each identity key.
   - **Two keys are counted first** ([#378](https://github.com/rojinc/ledgerly/issues/378)). Without this, an add with both could test any email exactly: pair it with a phone the admin controls, whose person they know, and which person the new row names, or a `CONFLICT` in that person's group, says whether the email is known. So an add with both an email and a phone is counted as an address check on the caller's own `persons` row before either key is looked up. A counterpart added at `POST /groups` is counted too, before its "can't be your own counterpart" check: that check answers only when the email is unknown, since the email is looked up first, so a guess paired with the caller's own phone pays the count either way. It's counted the same way, in the same window and against the same limit as an invite's or a reminder's ([invites](#invites), step 2: `ADDRESS_MISS_LIMIT`, 10 in 24 hours). In one database transaction, a guard write on the row, then the limit read as committed, then `addressMisses + 1` or a new window. At the limit, the add gets `RATE_LIMITED` before any lookup, so a known guess gets the same answer as an unknown one. A 409 runs it once more, then answers `CONFLICT`, still before any lookup. An add with one key, or a name alone, isn't counted.
   - **Taking it back:** only when both keys find the same existing person, as an invite takes its count back only for a right address, and step 3 takes the 1 back. The caller can read their own count, so this shows them that both keys are that person's, as an invite's refund shows a right address: a guess both keys confirm is free, and every other guess costs 1. Every other add keeps it: both keys found by nobody, since the count would then show that a guess paired with an unused phone is unknown; a split, one key found and the other not, or two different persons; and an add refused after the count for any other reason, a `CONFLICT` included.
   - **The cost:** the count is the one invites and reminders use, so about 10 two-key adds of new people in 24 hours also block the caller's invites and reminders until the window ends. That's rare for a house or a small employer, and switching routes gains a guesser nothing.
   - **Found:** use that person. Stage a guard write on that person's `rev`, then read the keys again: a key that moved to another person, or was removed, meanwhile (an adoption or a merge's step 1 writes the person) answers `CONFLICT`, and the add is tried again.
   - **Only one of two keys found:** use the found person and don't store the other key. Unverified data is never attached to an existing person, so a stranger's typo can't land on someone else.
   - **Not found:** create a placeholder person plus **one** unverified identity row: the email if one was given, otherwise the phone (none for a name alone). The other key is still validated but not stored, so a placeholder can only ever be claimed through one key ([only verified keys move](#only-verified-keys-move)). The add form says which key is used. Person IDs are random, with no timestamp ([data model](data-model.md#persons)), so a new person's ID doesn't show that the email or phone was unknown.
   - If the email and phone point at **two different persons**, use the email's person, whether or not either has an account. Do **not** merge: unverified data must never join two people.
3. Create the `members` row. If one already exists for that person in this group, return `CONFLICT`. A two-key add whose keys both found the same existing person takes its count back in this transaction (step 2): `addressMisses − 1`, never below 0, and only while the caller's row's `addressMissesFrom` is still the window it was counted in, as for an invite.
4. Set status `placeholder`, even if the person already has an account ([D-016](decisions.md)). The `groups` function never adds anyone except the group's creator to a team; people join themselves (see [Joining a group](#joining-a-group)).
5. Write an `activity` row (`member.added`).

Because of steps 2 and 4, the member row looks the same whether or not the person has an account, so neither the response nor the members list reveals it. That stops people using the form to find out who uses Ledgerly.

Accepted risks:

- A person has the same ID in every group, so someone who shares a group with them can add a guessed email to another group and see whether the IDs match. `CONFLICT` on adding someone twice tells the same thing within one group.
- Known and unknown keys take different times to add: an unknown one creates rows, and a known one costs a guard write and a second lookup. Known keys include placeholders others added, and the guard runs the same way for placeholders and registered people, so it shows only that someone has used the key before.
- An invite to an address that isn't the member's gets `VALIDATION_FAILED` ([invites](#invites), step 2), so an inviter can test guesses at a placeholder's email or phone: 10 wrong ones per 24 hours, counted together with wrong addresses typed for reminders ([#274](https://github.com/rojinc/ledgerly/issues/274)). It's the same kind of leak as the two above, which aren't counted. Each check is counted before the address is looked at ([invites](#invites), step 2), so a request in flight past the 10th gets `RATE_LIMITED` from its own count, before any address is checked: a burst can't pass the limit.
- **A two-key add can still test an email** against a phone the admin controls, or one whose person they know, as step 2 says: at most 10 counted guesses in 24 hours, together with the wrong addresses typed for invites and reminders. A guess both keys confirm as one person's isn't counted, as an invite's right address isn't. Accepted (the lead on #96, option (b) of [#378](https://github.com/rojinc/ledgerly/issues/378)).
- **That check can show that someone has an account.** A registered person holds every key they verified, and a placeholder only the one it was added with. So when an inviter guesses a member's second address and the check passes, the member has an account. The miss count above limits the guesses; accepted (the lead on #220).

## Claim (linking records to a new account)

Claiming is what lets "Sam" see the $50 you lent them when Sam finally signs up.

**Rule: claim only through verified identities.** Appwrite Auth verifies the email or phone number. A typed-in number proves nothing.

`identity POST /claim` (also run at the end of bootstrap):

1. Using the server SDK, read the user and collect their **verified** email and phone (`emailVerification`, `phoneVerification`).
2. For each verified identity key:
   - **No identity row:** create one pointing at the user's person, with `verified = true` and `verifiedAt` now.
   - **Points at the user's own person:** set `verified = true`, and `verifiedAt` now if it has none: a key keeps the time it was first verified (the [change notice](#email-and-phone-change-notice) ranks old addresses by it).
   - **Points at a person being merged into the user's person** (that person's `mergedInto` is the user's person, mid-merge): skip it; the merge moves it to them last.
   - **Points at another account's person** (a registered person, as when that account gave the address up by changing its email): leave it. A verified key never moves from one account to another, so the user gets no identity for it, and adding the address to a group still finds that person. Accepted for v1 ([#414](https://github.com/rojinc/ledgerly/issues/414), [threats](security-and-privacy.md#threats-and-controls)).
   - **Points at a placeholder person P:** **merge P into the user's person** (next section). Claim never adopts P: bootstrap does, for a user who has no person yet (bootstrap step 2, above), so by the time claim runs the user always has a person of their own ([#535](https://github.com/rojinc/ledgerly/issues/535)).
3. Join the user to every group where their person is still a `placeholder` member and the member row's `$createdAt` is strictly before the person's `claimedAt`. Those rows were added while the person had no account. Rows added later are left alone; the user joins those themselves ([Joining a group](#joining-a-group)). The rule reads only stored data, so a repeated or interrupted claim finishes the job. Functions never rewrite a member row's `$createdAt` and never delete and recreate a member row. These joins come before the claim carries on its merges ([merging](#merging-two-persons), steps 2 to 4), so in a group where the user's own row from before `claimedAt` was still a `placeholder`, a merge finds U joined and renames P there (the lead on [#349](https://github.com/rojinc/ledgerly/pull/349)).
4. Return the list of groups that were linked, so the app can say "We found 3 groups you were added to".

### Only verified keys move

A placeholder's identities were typed by whoever added it, and nobody has verified them. When a user claims placeholder P, by adopting it or merging it, **only the keys that user has verified move to their person**. P's other identities are deleted, in the same transaction that marks P: the adoption's (which sets `userId`) or the merge's step 1 (which sets `mergedInto`). So `resolvePerson()` can never follow one of them to the user, even mid-merge.

- **A verified key** is the key of an email or phone that Appwrite Auth shows as verified on the user's own account (`emailVerification`, `phoneVerification`), as read in Claim step 1. The key the claim came through is always one of them.
- **One typed key per placeholder.** Adding someone stores one key for a new placeholder ([adding someone](#adding-someone-to-a-group)), so the person who verifies that key is the only one who can claim it. With two keys, whoever verified *either* could take the placeholder, and with it the rows other groups had already added under the other key.
- **Why both rules:** otherwise someone could add `{ email: victim@x, phone: <their own phone> }` to their own group, verify the phone, and claim: `email:victim@x` would then point at them, every group that later adds the victim would add them instead, and the victim could never claim the address. Or they could add `{ phone: <the victim's>, email: <one of their own> }`, wait for other groups to add the victim by phone, then sign up with the email and take those groups. With one key per placeholder and only verified keys moving, neither works: a later add of the victim's key finds no identity and makes a new placeholder.
- **The trade-off:** a typed key the user hasn't verified is dropped, even when it really is theirs. A later add by that key makes a new placeholder, which is merged into them once they verify it ([#176](https://github.com/rojinc/ledgerly/issues/176) for phones).
- **Logs:** a claim's deleted identities are logged as IDs and counts, never keys.
- **Accepted risk, for later:** sign-in providers (Google, when OAuth comes) must be enabled only where they confirm the email is verified, or a provider account could claim someone's email.

So every identity of a person with an account holds a key they verified.

## Joining a group

A member joins a group only through the person's own action ([D-016](decisions.md)):

- **Claim:** verifying an email or phone joins every group they were added to while they had no account.
- **Accepting an invite** joins that invite's group.
- **Joining from the app:** someone who already had an account when they were added sees the group as pending and joins it themselves. The routes are `identity GET /groups/pending` and `identity POST /groups/{id}/join` ([Functions API](functions-api.md#identity)); they ship with pair groups in M2 ([#34](https://github.com/rojinc/ledgerly/issues/34)).

Joining, done by the `identity` function, in this order so a retry can always finish it:

1. Add the user to the group's team ("already a member" counts as done). A team that's gone means the group is being [purged](#purging-a-group), its member rows last: the row is skipped, not joined, and the claim goes on to the others (a join from the app answers `NOT_A_MEMBER`). If the team goes just after step 2 commits, the row stays joined and the purge deletes it with the others: the claim leaves the group out, and a join from the app answers with the row. An archived group with its team joins as before.
2. In one database transaction: stage a guard write on the group's row (a fresh `rev`) and check that it has no `deletingAt`, so a join and a [group delete](#deleting-a-group)'s step 2 never both commit; set the status to `active` (or `left` if `leftOn` is already set, so a former housemate can still see and settle up) and write one `member.joined` activity row. A group with `deletingAt` is left out as for a team that's gone (step 1). The same transaction reads every person merged into the joiner (`idx_mergedInto`, 100 at a time) and, on each placeholder among them (no `userId` or `deletedAt`, as only a placeholder is ever merged) whose `mergeGroupIds` lists the group, stages `mergeResumeAt` = now with a fresh `rev`, so a merge that skipped the group while the joiner wasn't joined there carries on there now ([finishing merges](#finishing-merges), [#358](https://github.com/rojinc/ledgerly/issues/358)). With no such person, that's one read. The mark writes P's row, so a merge batch or a clear on P that commits at the same moment fails the join's commit, which answers `CONFLICT` as a join that races any other write does, and is tried again. Accepted: it needs a merge into the joiner running on that P at that instant, and a claim's own merges run after its joins. If this step fails, the group is being deleted, or the member row is gone by now (an admin removed it meanwhile), remove the team membership from step 1 again, so no one keeps access without having joined. Only a row a parallel join has just joined keeps it.

All three ways write the same row, so the group can't tell which one happened.

Until they join, the person doesn't see the group's data (only its name, type and whether it's archived in their pending list, plus, for a pair group, the other member's display name, so they can tell who added them) and gets no notifications from it (an invite or an invoice sent to them on purpose is different). Records can still name them, exactly as for any placeholder. Before they join, the group can't tell whether they have an account. After they join, it may be able to (a merge changes their person ID); that's fine, because they chose to join.

## Merging two persons

A merge happens when a verified identity shows that placeholder **P** is the same human as an existing person **U**. P is kept for good, with `mergedInto = U`, so anything that still names P (an old statement's closings, a group U left on their own) can be resolved.

Merges can touch many rows, more than one Appwrite transaction allows (100 operations on Free, 1,000 on Pro). So a merge runs in steps that are each safe to repeat:

1. **Mark P.** In one database transaction, stage `P.mergedInto = U` and the deletion of P's identities whose key U hasn't verified ([only verified keys move](#only-verified-keys-move)), then read P's stored row again. If another adoption or merge got there first, roll back and leave P alone. After staging, the same transaction lists P's member rows (`idx_person_status`, every status) and records their groups as **P's groups**, `P.mergeGroupIds`. The list is final. It also reads U's member rows in those groups (by person, with the groups in chunks under the query filter's value cap) and records, in `P.mergeMembersJson`, P's `joinedOn` and `leftOn` in each group, and U's where U has a row there. Step 3 plans a posted row's items with these dates, as the members were before the merge, so an item split by `days` keeps every part (a lead decision, #242 B2; see **Inputs** in step 3). An add that found P stages a guard write on P's row (`persons.rev`, L2 in #252) and then resolves its keys again. If this step commits after that guard, the add fails its commit. If it committed first, the add's second resolve follows `mergedInto` (as every read does from now on), finds U rather than P, and answers `CONFLICT`. In both orders the add is tried again and lands on U. And if the add commits first, step 1's listing sees its row (or step 1's commit fails, since the add guarded P's row: that claim leaves P as it is, and the user's next claim marks P and sees the row). So no member row for P appears outside P's groups. Shares, inputs, templates and activity subjects are looked for only in those groups, in this claim and every later one that carries the merge on, never in all of U's, so a merge costs what P had, not what U has. From now on every function resolves P to U when it reads: `resolvePerson()` follows `mergedInto` to the end of the chain, so an email added for P mid-merge is added for U.
2. **P's member rows, one at a time.** P was a placeholder, so all its member rows were added while it had no account, and the merge joins U to each of those groups, except where U left on their own. Steps 2 and 3 go one of P's groups at a time: P's member row there, then the group's templates, inputs, activity subjects and shares, before the next group. So a merge cut off by the time budget leaves at most one group part done, and a merge is [open](#while-a-merge-is-open-in-a-group) in a group no longer than it must be. A group is also left part done when a finalize that starts after its member row moved puts it off (a later claim finishes it first, once the finalize ends), and while rows step 3 left as they are hold its inputs open: the walk goes on to the next group, and the refusals below cover the part-done ones.
   - **A group U left on their own** (U's row there has U's own `member.left` as the newest of their `member.left` and `member.joined` rows): leaving on your own is final for that row ([leaving a group](permissions.md#leaving-a-group)). So U isn't added to the team, U's row isn't touched, no share moves to U, and P keeps its row and its shares there, as a placeholder with no identities. Coming back after leaving stays unsupported, and a new invite can't help either: U's row blocks a second one (`uniq_group_person`).
   - **A pair or employer group U already has a row in:** such a group always has exactly two members, so P and U are its two sides, and joining them would leave it with one. It's left as above: U's row and team untouched, and P keeps its row and its shares there.

   These two are the merge's **kept groups** (the lead, 16:30 on #310): groups U left on their own, and pair or employer groups U already has a row in.
   - **Every other group:**
     1. If a statement in the group is `finalizing`, leave the whole group for the next run, P's member row included, so P's row doesn't move while the group's inputs and shares must wait. Do the same, logging P's and the group's IDs, if step 1's dates for the group can't be read: `mergeMembersJson` is `null`, fails `mergeMembersSchema`, or has no entry for the group. Step 3 never plans a posted row's items without them, so such a group keeps the merge unfinished. In each of these, P's reminders there still move, since step 3 finds them by person.
     2. Add U to the group's team ("already a member" counts as done). A team that's gone means the group is being [purged](#purging-a-group), its member rows last: P's member row and step 3's work there are left for the next run, as in 1, logging P's and the group's IDs, and the other groups go on. Once the purge has deleted the group's rows, nothing of P's is left there ([#334](https://github.com/rojinc/ledgerly/issues/334)).
     3. In one database transaction: stage a guard write on the group's row (a fresh `rev`) and check again that no statement in the group is `finalizing`, so a finalize that starts meanwhile fails one of the two commits, and that the group has no `deletingAt`: a group being [deleted](#deleting-a-group) is left as for a team that's gone (step 2), with U's team membership from step 2 removed again. Then, if U also has a member row in the group, keep U's row, set its `joinedOn` to the earlier of the two and delete P's row; otherwise repoint P's row to U. The write to the kept row also sets a fresh `rev`, so it's a real change even when U's row was already `active` with the earlier `joinedOn`, and a leave or removal that guarded U's row fails its commit ([concurrency](ledger.md#concurrency)). Then set the kept row's status as in [joining](#joining-a-group) and, where U's row there wasn't joined yet (U had none, or a `placeholder`), write `member.joined` by U, and stage the same mark on each other person merged into U whose `mergeGroupIds` lists the group, as joining step 2 does: another merge into U may have skipped the group earlier in the same run, while U wasn't joined there ([#358](https://github.com/rojinc/ledgerly/issues/358)). A row U had already joined, a claim's own join just before included (Claim step 3), gets no second one. The same transaction stages a guard write on U's person row (a fresh `rev`) and checks that U has no `deletedAt`: a merge never joins a person whose account is being deleted, and a deletion that races it fails one of the two commits ([deleting an account](#deleting-an-account-m4), step 2). If U has `deletedAt`, the transaction rolls back, the team membership is taken back, and every merge into U stops. Both member rows are staged before they're checked, so a ledger write that guards one of them ([concurrency](ledger.md#concurrency)) runs again, and so does this step if one of them changed. If the transaction fails, take the team membership back, unless U has a joined row there. Once it commits, add U to the team again ("already a member" counts as done), as a join does: the first add may have found an old membership that the [nightly check](scheduling.md#step-6-nightly-check) then removed as stale. If the team is gone by then (a purge, #334), the group isn't one U joined, and step 3 goes on there: its batches take turns with the purge's on the group's `rev`, and the purge deletes P's row, now U's, with the others.

   A row is finished once it no longer points at P, so a retry carries on with the rest.
3. **P's shares, inputs and identities, in batches** of at most 90 operations per database transaction, guard writes and `balances` row deletes included, skipping kept groups. Shares, inputs, templates and activity subjects are looked for in P's groups (`mergeGroupIds`), one group at a time (or IDs in chunks under the query filter's value cap) and never all of the list in one query, so a long list only spreads the merge over more claims. Identities are found by person, and so are reminders, except those in a kept group:
   - **Guards first:** a batch that changes a group's shares or inputs stages a guard write (a fresh `rev`) on that group's row, then checks that no statement in the group is `finalizing`. If one is, that group's work is left for the next `/claim` or hourly run. A batch that rewrites inputs or a schedule template also stages U's person-row guard and checks `deletedAt`, as step 2 does, so no input or template comes to name a person whose account is being deleted. Every writer of shares writes the group `rev` ([concurrency](ledger.md#concurrency)), which is how `GET /balances` knows a read was complete.
   - **Balances:** after the guard, a batch that changes a group's shares (repoints, combines, or deletes them with a void) reads that group's `balances` row and, if there is one, deletes it in the same transaction ([balances](ledger.md#balances)). `/balances` sums the shares until the nightly check builds the row again, so balances never show P's old figure under U's name. A row deleted meanwhile fails the batch, which runs again.
   - **Shares:** repoint `shares.personId` from P to U. If P and U have shares in the **same transaction**, combine them into one share (sum given and received) to keep [I-5](ledger.md#invariants). Both are staged, then read again, so two merges can't add P's share twice. This includes shares of locked transactions: the merge is the one writer allowed to change those, and only this way ([I-7](ledger.md#invariants)). No transaction's total changes, so every group still sums to 0 after each batch (I-1). A group's shares move after its templates and inputs, and only in that group, and only where U has a member row there: in one of P's groups where neither has a row any more (U's, once P's, removed since), P's shares stay. Each share batch stages a fresh `rev` on U's member row there, then checks that U is still joined, so a removal or a leave of U's that overlaps it fails one of the two commits, and one that commits first leaves P's shares where they are. Before the identities move, a member row or share of P's found outside the kept groups keeps the merge open and is logged by ID.
   - **Inputs:** P becomes U inside the stored inputs that name people: `transactions.inputJson` and `items.splitJson` of every transaction that **isn't void** (unposted ones, schedule occurrences included; posted ones, since an edit reads them again; and locked ones, since voiding their statement unlocks them), and `schedules.templateJson`. **Only in a group where U is joined** (`joinedHere`, as for activity subjects below; the lead on [#347](https://github.com/rojinc/ledgerly/issues/347)): in one of P's groups where U isn't, nothing there is renamed or voided. Its inputs, item splits and templates keep naming P, are logged by ID (P, U and the group: counting them would mean the scan this skips), and don't hold the merge open (step 4). P there is a non-member, as before the merge, so no input or template that group's team can read links the placeholder to U's account ([D-016](decisions.md#d-016-being-added-to-a-group-doesnt-make-you-a-member-you-join)). Nor is the group [open](#while-a-merge-is-open-in-a-group), since that test on U is `joinedHere` too: a write naming P there answers as for any non-member (an edit must name someone else, and auto-post fails it), and nothing renames P to U there later. Claim step 3 joins U's own `placeholder` rows before the claim carries the merge on, so such a group is one where U has no row or a row added after U signed up, one U left on their own, or one whose claim stopped before its joins (the hourly run joins nothing). A group U joins later, even after the merge has finished, marks P (`mergeResumeAt`, [joining](#joining-a-group) step 2), so the merge carries on there once U is joined, and renames P there then ([#358](https://github.com/rojinc/ledgerly/issues/358)). What can be left in such a group is posted rows with no share of P's (a 0-basis-point or 0-cent part): P's row there was removed before step 2, or U's after it with U added again later, and each removal is refused while P has a share or is named in an unposted row or a template. One exception: where step 2 moved P's row, the template batch was put off, U then left on their own, and an admin removed U's row and added U again, P's unposted rows and templates there are left until U joins again, which marks P and renames them then ([#358](https://github.com/rojinc/ledgerly/issues/358)). No money moves in either case: P has no share there. The check is made on each run, before the group's templates and inputs, with no guard on U's member row: as for subjects, losing a race with a leave, removal or join only renames rows in a group where U was joined when checked. A locked row is renamed exactly as a posted one is, and nothing else on it changes ([I-7](ledger.md#invariants)): its total, status and `statementId` stay, and the rename changes no share, so a final statement's numbers don't move. A locked row the merge can't read (JSON it can't parse, or an input today's schema refuses) is logged by ID and left as it is. That row doesn't hold the merge open, and its group's inputs count as done, since nothing can change a locked row. A schedule's rewrite is staged with the scheduler's schedule guard (a write to the schedule row, then a check of the stored row), so an expansion in flight can't race it. Where U is already listed, the entries are added up: payer amounts, `exact` amounts, `percent` basis points and `weights` add; an `equal` split becomes `weights` (U 2, everyone else 1); a `days` split lists U once, since presence comes from U's kept member row. A loan's lender is its payers or, for a posted one that stores none, its creator (`createdBy`), as an edit has it. A `payment` or `loan` that isn't locked and whose two sides would both become U is voided instead, posted or not (its shares net to 0 for U either way). A locked one is never voided: a loan is renamed, and a payment keeps naming P, since a payment's two sides must differ. That payment doesn't hold the merge open. **A posted expense, bill or loan without items** (locked ones included) **that is P's** (its input names P, or P has a share in it) **must plan the same parts after the merge:** an edit plans it again with the members as step 2 left them (and, where it stores no payers, its creator paying), so the renamed input is planned the same way and compared with what its shares gave each person, P's added to U's. Where they differ, an edit would move money between people: a default split would count U once, a `days` split would count the days of U's kept row (which starts at the earlier `joinedOn`, so it can change a bill only one of them, or neither, had a part of), a loan's default would leave out a U who lent, or a leftover cent would fall elsewhere. So the split is written out. A row with no split gets an `equal` split of those with a part, renamed as above (so `weights` with U at 2 where both had one), if that plans the same parts. Any other row whose plan differs gets `exact`, from the shares. An edit that keeps the total then keeps every net; one that changes an `exact` split's total must pick the split again. A row that isn't P's is left as it is, even where today's plan differs for another reason (a `leftOn` set since it was posted, say). Unposted rows and schedule templates have no shares to go by and keep the plain rename: a default or `days` split there counts U once when it posts. **Except where the rename leaves a `weights` split invalid** (U's weight, P's added to it, past `MAX_WEIGHT`): there the split is written out as `exact`: `allocate()` splits the row's total (an unposted transaction's `totalCents` column, a template's own `totalCents`, or an item's amount, for an item's split) by the weights as they were, P's and U's apart (together they're past the cap `allocate()` checks, so the renamed weights #348 first named can't be split), in their stored order as `splitAmount` plans them (`allocate()` gives a tied cent to whoever comes first), then P's part is added to U's. So each person's part is what the split gave before the merge, in integer cents, and the row stays editable ([#348](https://github.com/rojinc/ledgerly/issues/348), the lead's (a)). Otherwise the merge couldn't write the row, an edit of it would be refused while the merge is open there, and only a void would free it. An edit that changes such a row's total must pick its split again, as for any `exact` split, and so must a schedule edit that changes a template's total, since its trial plan refuses an `exact` split that doesn't add up. **A posted row's items** (locked ones included) are planned twice: as they are, with the members as they were before the merge (P's and U's member rows with step 1's dates, everyone else's as they are now), and renamed, with the members as step 2 left them, as an edit would plan them. Where the parts differ (an `equal` or `weights` split's leftover cent can fall elsewhere once two entries are one, and a `days` split counts U's kept row once), the item's split is written out as `exact` from the parts before, so no one's part of a posted item changes (a lead decision, #242 Q2 and B2). Both posted-row rules also cover a split the rename leaves invalid (weights past `MAX_WEIGHT`): it's written out as `exact` too, with everyone it names at 0 where the total (or an item's amount) is 0. Each rewritten row is staged, then read again, so a row that was posted, edited, voided, locked or unlocked meanwhile makes the batch run again. One pure helper in `packages/core` does this rewrite.
   - **Where the input scan got to:** a group's transactions are scanned in `$id` order, a page of 100 at a time. Once a page's batches have committed, step 3 writes that page's last `$id` to the group's entry in `P.mergeCursorsJson` (`after`), and adds to its `left` the IDs of the page's rows left as they are (an unlocked row it can't read or rename). A later claim or hourly run starts the group's scan after `after`, so a big group finishes over several runs rather than starting again at its first row each time (a lead decision, #242 G). Each run reads the rows in `left` again first, 100 at a time, so one voided, fixed, locked or deleted since drops out, and one still left keeps the merge open. The group's inputs are done once a scan has reached its end and `left` is empty, or at once in a group where U isn't `joinedHere`, which isn't scanned and whose entry isn't written. The scan pages by `$id` (`Query.greaterThan`, [scaling](scaling.md)), so a cursor row deleted since changes nothing. The entry is written as P's other entries were read: staged, then P's row is read again, and a change meanwhile makes it read and merge them again, so two runs at once never lose each other's `left`. Each writes only a point it reached, so whichever wrote last is safe to carry on from. No row behind the cursor can come to name P anew: from step 1 on, every write resolves P to U, and from step 2 on, P has no member row in the group to be named by. A statement void can unlock rows the scan passed while they were locked, and two kinds of those still name P: a payment between P and U, and a row the merge couldn't read. The scan doesn't come back to them, and step 4 counts them as it counts a locked one, so they don't hold the merge open: the same state a void after a finished merge leaves (Q2 (a) and Q3 on #263). An entry that's missing, `null` or fails `mergeCursorsSchema` starts that group's scan from its first row, which is only slower. When two runs' entries for a group are merged, the `after` of the run writing last stays.
   - **Activity subjects:** in P's groups, `activity.subjectPersonId` goes from P to U (`idx_group_subject`), in batches of at most 90 writes, each row staged and then read again. No group guard is needed: nothing else ever updates an activity row, so only a purge (which deletes it) or another run of the same merge can race it, and either makes the batch run again. It's the one change an activity row ever gets outside a purge ([data model](data-model.md#activity)), so the feed names U on member rows written while P was a placeholder, not "A former member". Kept groups are skipped: P keeps its row and its activity there. As for shares, subjects move only where U is joined in the group: U's row there is `active` or `left`, not `placeholder`, and not one U left on their own (the check share batches make, `joinedHere`; the lead on #338). In one of P's groups where U isn't (P's row removed after step 1 and U with no row there, U's row a `placeholder`, U's row removed since, or U having left on their own since), they stay on P, are logged by ID and don't hold the merge open (step 4), so no activity row that group's team can read links the placeholder to U's account ([D-016](decisions.md#d-016-being-added-to-a-group-doesnt-make-you-a-member-you-join)). Unlike share batches, these don't stage a guard on U's member row: a leave, removal or join that lands between the check and a batch can only move rows in a group where U was joined when checked, whose team already saw U there (U's own row, or step 2's `member.joined`), so losing that race links nothing new. Inputs and templates are left the same way (above, [#347](https://github.com/rojinc/ledgerly/issues/347)).
   - **Reminders:** repoint `reminders.toPersonId` from P to U, so the recipient limit counts the reminders P was sent toward U ([reminders](#reminders)). They're found by person (`idx_toPerson_sentAt`), not in P's groups; one in a kept group stays on P, as P's shares there do.
   - **Identities, last:** once nothing else outside the kept groups names P (as step 4 counts it), repoint `identities.personId` from P to U. After step 1, only keys U verified are left, and at least one of them (the key the claim came through) points at P. So P still having an identity, or a `mergeResumeAt` mark (step 4), is what marks a merge unfinished.
   - Columns that only ever hold a person with an account (`createdBy`, `updatedBy`, `actorPersonId`, `invitedBy`, `ownerPersonId`, `reminders.sentBy`) can't name a placeholder, so they're left alone.
4. **Finished.** P is never deleted. A merge is finished when nothing outside the kept groups still names P: no identity, member row, share or reminder's `toPersonId` (checked by person, in every group but the kept ones), and, in P's groups (`mergeGroupIds`), no input or item split of a transaction that isn't void, locked ones included, apart from a payment between P and U and a row the merge can't read that were locked when the scan passed them; and no schedule template; and no activity row whose subject is P. In a group where U isn't `joinedHere`, the inputs, item splits, templates and activity rows naming P don't count: step 3 leaves them there on P, so they don't hold the merge open. P's shares there still do, as above. A batch put off for a group (a `finalizing` statement, or the time budget) therefore keeps the merge unfinished, whatever order the batches ran in. A merge whose identities have moved counts as unfinished again while P has `mergeResumeAt` set: U has since joined one of P's groups ([joining](#joining-a-group) step 2, or step 2 above), so that group's inputs, templates, subjects and shares count now, and the merge carries on there with the same steps. The mark is cleared where the identities would move, once nothing outside the kept groups names P, by a write staged and then checked: it's cleared only if P's mark and `rev` are still as the run read them (each mark writes a fresh `rev`), so a join that marks P again meanwhile, even within the same millisecond, isn't lost ([#358](https://github.com/rojinc/ledgerly/issues/358)). Until then, `/claim` (for persons whose `mergedInto` is the caller's person, `idx_mergedInto`) and `identity`'s hourly job ([finishing merges](#finishing-merges)) carry on with it; after that, they leave P alone. Meanwhile the [nightly check](scheduling.md#step-6-nightly-check) counts P's shares as `merging`. `/claim` stops starting batches after a time budget well inside the function's timeout.

A merge cut off partway leaves some of P's shares on P and some on U. Each batch keeps every group at 0, but until the next `/claim` or hourly run finishes it, balances show P and U as two people. A statement drafted or finalized between batches resolves P to U wherever P has no member row ([statements](statements.md#core-rules), rule 2), so it still adds up.

Statement snapshots are **not** rewritten. They are historical documents and keep the old display name; openings follow `mergedInto` when they're read ([statements](statements.md#core-rules)). The exception for locked transactions (their shares and stored inputs) is in [I-7](ledger.md#invariants) and [D-010](decisions.md#d-010-closed-periods-never-change).

### While a merge is open in a group

P's merge is **open** in a group G, per group (a lead decision, #301), while all of these hold:
- P has `mergedInto` set, and G is one of P's groups (`mergeGroupIds`);
- P has no member row in G, and U (P's `mergedInto`) is joined there as step 3 tests it (`joinedHere`: an `active` or `left` row, not `placeholder`, and not one U left on their own): step 2 has given P's place to U, and it always leaves U's row joined. A `placeholder` row of U's doesn't count, so a write naming P there never answers `merging` for a U who hasn't joined (D-016). Nor does a row U left on their own: step 3 leaves P's inputs and templates there on P, and they'd answer `merging` for good (AI E's review of [#349](https://github.com/rojinc/ledgerly/pull/349)). Unless U's account is being deleted (`deletedAt`) and U hadn't left that group on their own before it: deletion's keep writes U's `member.left` in every kept group, but a merge into a deleted U stops where it was (below), so step 3 never ran there, and U's kept row still holds P's place. Removing it would leave P's shares with no member row ([I-3](ledger.md#invariants), [#362](https://github.com/rojinc/ledgerly/pull/362)). So for a deleted U only U's own `member.left` and `member.joined` rows from before `deletedAt` count: where U left on their own before the deletion, step 3 had already left P's rows on P there, and P has no share there (a leave of U's own after step 2 is refused while P has one), so the group stays as it was. A kept group keeps P's row, and so does a group step 2 hasn't reached yet, so neither is open. Nor is a group where P's row was removed before step 2, while U isn't joined there, so a write naming P there answers as for any non-member (one U joins later is open until the merge, which the join marks, has carried on there: [#358](https://github.com/rojinc/ledgerly/issues/358));
- G still names P, as each writer below says.

Whether P still has an identity doesn't matter. So a merge that can never finish (a row it can't read, say) holds only the groups that still name P, and a merge into a U whose account was deleted midway (deletion step 5 removes P's identities) stays open where it stopped (the desk's recommendation, #301).

In an open group, the writers below would count P as someone other than U. So they refuse, with `CONFLICT` and `details: { reason: 'merging' }`, and the app asks to try again shortly (a lead decision, #242 B1):
- **Leaving** (`POST /groups/{id}/leave`) and **removing a member** (`DELETE /groups/{id}/members/{memberId}`), when a person merged into the member (`idx_mergedInto`) has an open merge in G where P still has a share (`idx_group_person_date`). A removal is also refused while P is named in G's unposted transactions or schedule templates, as the removal rule checks for the member themselves ([leaving a group](permissions.md#leaving-a-group)). Otherwise a leave would check U's balance without P's shares, and the next claim would move them onto a U who has left. A removal would leave P's shares, or an unposted row naming P, with no member row ([I-3](ledger.md#invariants)).
- **`PATCH /transactions/{id}` and `/post`**, the scheduler's auto-post included, when the row's stored shares, stored input or item splits name a person P whose merge is open in its group (the row itself is what names P there). Both plan the row again with today's members, where U counts once, so P's part would move to others before step 3's rule for a posted row could write it out. `/void` and `/receipts` don't plan shares again, so they go ahead. The check reads the row's stored input as the edit itself does, so a row whose stored input can't be read fails as it does today (`INTERNAL`): a row step 3 left as it is for that reason can only be voided, never fixed by an edit.

Each writer checks after its own guard writes. A leave or a removal, when a person merged into the member lists the group, stages a guard write on the group's row (a fresh `rev`) as well as on the member row, before it reads the balance or shares: step 3's batches write the group row, and step 2 writes both. With no such person, no batch can move shares onto the member there. A ledger write guards the group row, as always. So a writer that checked just before step 2 or a step 3 batch committed fails its commit and runs again, and is refused, or goes ahead once the batch has moved the last of what named P. A ledger write also checks before it plans the row, since planning refuses a person with no member row as not in the group, and the answer should be this one. With no merged persons, the check costs a leave or a removal one `persons` read (`idx_mergedInto`), and a ledger write two reads of the persons its row names, one before planning and one after the guard writes. For each merged person found, it reads P's and U's member rows in G and, for a leave or a removal, P's shares there (`limit 1`). Where U's row is `left`, it reads U's newest `member.left` or `member.joined` there too, to tell whether U left on their own, and U's `persons` row, so that for a deleted U only rows from before `deletedAt` count. The hourly job ([finishing merges](#finishing-merges)) keeps the window to about an hour, unless a group's statement stays `finalizing`. A merge into a deleted U, or one stuck on a row it can't change, keeps refusing in the groups it holds; voiding the rows there that name P ends it in that group.

### Finishing merges

A merge cut off partway carries on within about an hour, even if U never calls `/claim` again, and a big one over several runs ([#246](https://github.com/rojinc/ledgerly/issues/246)). `identity` runs every 60 minutes (`interval: 60`, so Appwrite picks the minute: [intervals, not cron](../engineering/environments-and-deploys.md#function-settings)), sent as `POST /` with the `schedule` trigger ([functions API](functions-api.md#identity)):

1. **A scheduled run finishes merges.** A signed-in call gets `FORBIDDEN`. Other runs without a JWT are handled as [function-side checks](permissions.md#function-side-checks) says.
2. **The budget** is the same as `/claim`'s, well inside the function's timeout, and it counts the walk below.
3. **Unfinished merges:** a merge is carried on exactly while P still has an identity, since identities move last (a merge into a deleted U has none left: deletion step 5 deletes them), or has `mergeResumeAt` set (a later join of U's in one of P's groups, [#358](https://github.com/rojinc/ledgerly/issues/358)). The walk below reads every merged person's row anyway, so the mark needs no index. The run pages through persons with `mergedInto` set (`idx_mergedInto`, 100 at a time) and, for each page, pages through the identities on them (`idx_personId`, only `personId` selected), keeping the persons that still have one, or the mark.
4. **For each U** (the `mergedInto` person), in random order so a merge that can never finish doesn't take every run's budget: read U's person row just before its turn, skip U when `deletedAt` is set or there's no `userId`, then carry on U's merges with the same code `/claim` runs. A skipped U's merges never go on, so the run also clears the mark of each of its Ps that has one (staged, then checked as in merge step 4), and such a P isn't counted as skipped again on later runs. It never marks a new merge (merge step 1, Mark P).
5. **After a run finishes any of U's merges,** as `/claim` does (the co-lead on #330), it reads U's Appwrite user once (`users.get`) and marks verified U's identities not yet verified whose key U's account verifies, as claim's step 2 does. Other merges of U's still open don't matter: only keys U's account verifies are marked. So statement emails can use them before U's next login. A user that's gone (404) or labelled `deleted` is skipped.
6. **Logs and result:** counts only, per merge: `unfinished` found, `finished`, `skipped` (U deleted, or with no `userId`), `cutOff` (left unfinished once the budget had passed) and `stopped` by an error; the rest were carried on and wait (a group put off). The run logs them once (`logProblem`'s `merge_run`), with `personsRead`, the merged persons the walk read ([scaling](scaling.md)), and warns (`merge_walk_cut_off`) when the walk itself ran out of budget before its end. Each merge's own log line holds IDs and counts, as for `/claim`. A U whose merges stopped on an error is logged with U's ID and the error's name, as a warning (`merge_stopped`) for a race with a claim (`CONFLICT`) or a deletion (`NOT_FOUND`), and otherwise as an error (`merge_run_failed`), the alert; the run goes on to the next U. A claim whose merges stop logs them the same way, and the sign-in carries on ([#535](https://github.com/rojinc/ledgerly/issues/535)). A walk that fails is logged as `merge_run_failed`, with no IDs, and the run still retries change notices (step 8 of the [change notice](#email-and-phone-change-notice)). If step 5 fails after U's last merge finished, a later run no longer finds U, so those keys wait for U's next login.

**Runs that overlap are safe.** This job, U's own `/claim` and `account`'s hourly job can reach the same merge at once; two runs of this job can't, since its timeout is far under the hour. Every merge write is staged, then checked against the stored rows, so a change another run made first fails the batch, which runs again and finds it done. Steps 2 and 3 guard U's person row and check `deletedAt`, so a deletion that starts meanwhile fails one of the two commits ([deleting an account](#deleting-an-account-m4), step 2).

U didn't call it, but U started the merge by verifying the key, so finishing it is U's own action ([D-016](decisions.md#d-016-being-added-to-a-group-doesnt-make-you-a-member-you-join)). U isn't told which groups they joined. Accepted for v1: a merge that can never finish is tried every hour, and its log line is the alert. That line (`merge_carries_on`) is a `log`, not an error, so it shows in the run's `.logs`, not its `.errors`; the error-lines read lists it ([merges that don't finish](../engineering/error-lines.md#merges-that-dont-finish)).

## Invites

An invite is a convenience: a link that tells someone they've been added and helps them sign up. Claiming works without one, as long as the person verifies the key that was stored for them: the email, or the phone if no email was given ([adding someone](#adding-someone-to-a-group)). An invite's row, which holds the address it went to, is deleted 30 days after it's accepted or expires ([scheduler step 5b](scheduling.md#step-5b-invite-clean-up)); an old link then gets `INVITE_INVALID`, as an unknown one does.

`identity POST /invites` with `{ groupId, memberId, email?, phone? }` (exactly one of email or phone):

1. The caller must be allowed to add members in that group ([permissions](permissions.md#roles)) and must have a verified email ([F-02](../product/features.md#accounts-and-profile)); otherwise `FORBIDDEN`.
2. `memberId` must be in that group (otherwise `NOT_FOUND`) and still a `placeholder` (otherwise `VALIDATION_FAILED`). The invite goes only to the address the caller typed. After normalising, it must be an identity of that member's person, otherwise `VALIDATION_FAILED`. Ledgerly never picks an address the caller didn't give, so it never emails an address the inviter doesn't already know.
   - **Wrong addresses are counted** ([#274](https://github.com/rojinc/ledgerly/issues/274)), per sender, together with wrong addresses typed for reminders ([step 5 there](#reminders)). Every answer with this step's wrong-address message is a miss, whatever the reason, so the sender's own row never tells the reasons apart. A window is live from `addressMissesFrom` until `ADDRESS_MISS_LIMIT.hours` (24) later. After the member checks and before the address check, a sender whose `persons` row holds at least `ADDRESS_MISS_LIMIT.count` (10) misses in a live window gets `RATE_LIMITED`, with step 3's message: a right address gets the same answer as the wrong ones.
   - **Counting first:** every address check is counted **before** the address is looked at, and a right address takes its count back when a new invite or reminder is sent to it (a reminder retry never does: [reminders](#reminders), step 3) ([#274](https://github.com/rojinc/ledgerly/issues/274)). A miss recorded after the check could be dropped by a conflict the sender causes on their own row (a profile edit), and on a retry a `CONFLICT` would then mean "wrong address". So, after the member checks and before the address check, one database transaction stages a guard write (a fresh `rev`) on the sender's `persons` row, then reads it again as committed ([concurrency](ledger.md#concurrency)). At the limit in a live window, it rolls back and answers `RATE_LIMITED`, with the route's own message (step 3 here, reminders' 6.3), so nothing is written. Otherwise, in a live window, it stages `addressMisses + 1`; one at or after the window's end, or with `addressMissesFrom` `null`, starts a new window: `addressMisses` = 1 and `addressMissesFrom` = now. Then it commits. A 409 runs it once more, then answers `CONFLICT` **before any address is looked at**, so a conflict tells the sender nothing.
   - **Taking the count back:** a right address that's sent to takes its 1 back (`addressMisses − 1`, never below 0, `addressMissesFrom` unchanged) in the transaction that commits the invite (step 3, which already guards the sender's row), but only while the guarded row's `addressMissesFrom` is still the window its count was taken in, compared as instants, since Appwrite may return a datetime in another form than the one written. Once another check has started a new window, it takes nothing back, so it can't cancel a check counted in that new window; that only over-counts. A request refused after the check for any other reason (a wrong address, a deleted target or end person, a removed or joined target row, `UNAUTHENTICATED`, the rate limits, a conflict, even with the sender's own parallel request, or a reminder whose step 7 loses to a parallel call with the same `id`) keeps its count. So at most `ADDRESS_MISS_LIMIT.count` addresses go unsent per window, bursts and conflicts included; over-counting a refused right address is the accepted price. The row holds a count and a time only: no address, target or route.
   - **A successful send takes back only its own count**, never earlier misses, so a sender who knows one real address can't mix it in and keep guessing. A window starts at its first counted check, right or wrong, so up to 20 unsent checks can fall in 24 hours, around a window's edge (accepted, the lead on #274).
3. **Guards, then checks, in one database transaction.** So that a burst of parallel requests can't pass the count together, first stage a guard write (a fresh `rev`) on the inviter's and the target's `persons` rows. Then follow the target's `mergedInto` to the end, as stored (`mergedTarget()`, as `resolvePerson()` does). If it ends at someone other than the target and the inviter, stage a guard write on that **end person** too: a placeholder mid-merge holds only keys the end person verified ([only verified keys move](#only-verified-keys-move)) until the merge moves them, last ([merging](#merging-two-persons), step 3), so the address is the end person's. A merge that marks the target after its guard was staged fails this commit. Then:
   1. Read the guarded rows again, as stored (not through the transaction). An inviter with `deletedAt` (their account deletion started while the request ran) gets `UNAUTHENTICATED`, since one that started before was already refused as `NOT_A_MEMBER` ([permissions](permissions.md), step 2); then the target's member row, read again as stored: gone, in another group or naming another person gets step 2's `NOT_FOUND`, and no longer `placeholder` its `VALIDATION_FAILED`. A target whose person is gone gets that `NOT_FOUND` too: an account deletion keeps the person row, and so does [scheduler step 5c](scheduling.md#step-5c-placeholder-clean-up), so this shows no deletion. Then a target or end person with `deletedAt` gets the same `VALIDATION_FAILED` as a wrong address (step 2), and keeps the count its check took (step 2), so neither the answer nor the sender's row shows the deletion. The address-miss limit needs no second check here: every check paid its count before it ran (step 2), so a right address in a burst of wrong ones is sent, and takes its count back, if its own count got in before the limit. This is reminders' order (6.2). So no invite goes to the address of someone whose account deletion has started, even before [deletion step 5](#order) removes the identities of persons merged into them. A deletion that commits after the guard was staged fails this commit, and the one retry then refuses. A removal or a join also writes the target's person ([removing completely](permissions.md#leaving-a-group)), so one that commits after these reads fails this commit too, and the retry reads the row again.
   2. **Rate limits:** at most 20 invites per inviter in the last 24 hours, and 3 per identity in the last 7 days. Otherwise return `RATE_LIMITED`, before anything in this step is committed (the address check's count, from step 2, stays).
4. Create a random 32-byte token (base64url). Store only its SHA-256 hash, with `expiresAt` 14 days ahead. Commit the invite row before sending, so a failed send still counts toward the limits (it returns `INTERNAL`).
5. Send `https://<app>/invite#<token>` by email (Resend), or by SMS after v1 ([#40](https://github.com/rojinc/ledgerly/issues/40)). The token goes in the URL fragment, which browsers never send to servers or in `Referer` headers, so it stays out of logs. The message names the inviter and the group, nothing else. It is sent the same way, with the same response, whether or not the person has an account.
   - **Subject:** "You've been invited to a group on Ledgerly", fixed: both names are free text, so they stay out of it.
   - **Body:** "{inviter} added you to the group “{group}” on Ledgerly and invited you to join.", then "If you weren't expecting this, you can ignore this email." and the link. `{inviter}` is the inviter's `members.displayName` in that group and `{group}` the group's name. Each is put on one line and cut to 40 characters as people see them (with "…"), as a reminder's `{sender}` is ([reminders](#reminders), step 9), and HTML-escaped.

`identity POST /invites/accept` with `{ token }`:

1. Hash the token and find the invite. If it is missing or expired (from `expiresAt` on), return `INVITE_INVALID`. Every `INVITE_INVALID` here has the same message, so it never says which case it was.
2. The caller must be signed in and have **verified** the invite's identity: the account's verified email (for an email invite) or phone (for an SMS one), normalised, is the invite's `identityKey`. If the invite is **already accepted**, return `{ groupId }` when the identity is the caller's (they have verified it, and its identity row is on their person, or on a placeholder merged into it), so a retry or a second accept at the same time gets the same answer; anyone else gets `INVITE_INVALID`. Either way nothing is written. Otherwise, if the caller hasn't verified it, return `{ needsVerification: 'email' | 'phone' }` (by the invite's channel) before writing anything, and the app runs Appwrite's verification flow and then calls accept again.
3. Run Claim. If the invite's identity still isn't the caller's (another registered person holds it), return `INVITE_INVALID`. Then, if the caller's own person has a member row in the invite's group that is still `placeholder`, join it. (The invite's `memberId` may have been merged away or removed since.) Any other row is never touched: it has joined already, or left on its own, which is final. If a merge is cut off before it moves the invited row, the next `/claim` joins it. Accept answers the invite's group even when it joins nothing: the caller has no row there (removed, or merged away), left on their own, or the group is being purged and its team is gone (`joinGroup` returns `false`, [#352](https://github.com/rojinc/ledgerly/issues/352)). Nothing is joined and no access is given, and the accept screen ([#174](https://github.com/rojinc/ledgerly/issues/174)) must handle a group the caller can't open.
4. Set `acceptedAt` (to the time step 1 checked against `expiresAt`, so it's always before it), last, so an accept cut off before it can simply run again: every earlier step is safe to repeat. Stage it, then check the stored row; if another accept set it first, keep that time and return `{ groupId }`, as in step 2.

## Reminders

Someone owed money in a lend & borrow group can email the other person a reminder of the amount, at an address they type (F-63, [#56](https://github.com/rojinc/ledgerly/issues/56)). Email only for now: SMS reminders follow SMS invites ([#40](https://github.com/rojinc/ledgerly/issues/40)) and add `phone` to the body in their own contract change.

`identity POST /reminders` with `{ id, groupId, email }` (`sendReminderBodySchema`; `id` is a client `ID.unique()`):

1. **The body** must parse, otherwise `VALIDATION_FAILED`.
2. **Who:** a joined member of the group (`requireMember`) with the role `admin` or `member`, with a verified email, as for invites. A `placeholder`, `left` or non-member caller gets `NOT_A_MEMBER`, a viewer or an unverified caller `FORBIDDEN`, an archived group `ARCHIVED`. A group that isn't a `pair` gets `VALIDATION_FAILED`: houses have settle up.
3. **A retry:** if a `reminders` row with ID `id` exists, anyone but its sender in its group gets `CONFLICT`. The sender gets its stored `{ sentAt }`, whatever the rest of the body says (an exception to [idempotency](functions-api.md#idempotency)). The email is sent again, with the same Resend key, only when **both** hold: `sentAt` is under 23 hours old, so the key is still live and Resend delivers each `id` at most once; and step 4, step 5's address check and the recipient's `deletedAt` check (step 6.2) pass again for the address typed now. Otherwise nothing is sent. So a retry can't be used to send one reminder again after the key expires, or to an address the first one wasn't checked against. A retry's address check is counted first too ([#274](https://github.com/rojinc/ledgerly/issues/274)), since a match sends again and so takes longer: as step 5 counts one, before the address is looked at. **A retry never takes its count back,** whether or not its address matches or it sends. Under the reused key, Resend refuses a send to a different address and replays one to the same address, so a retry's send doesn't show that anything was delivered. A take-back there would let the sender test the recipient's other addresses for free, read off their own `persons` row. A retry answers its stored `{ sentAt }`, unless the email it sends again fails (step 8's `INTERNAL`). Only a matching address gets that far, and it has already paid its count, so that answer tells the sender nothing for free. So a retry, too, never tells a deleted recipient from a wrong address. A sender at the limit, or whose counting conflicts twice, gets the stored `{ sentAt }` with no address check and nothing sent, so a conflict tells them nothing either. The app's own retries, which follow only a send that failed, cost 1 each.
4. **Owed to the caller:** the caller's net in the group, read with the same helper as `GET /balances`, must be above 0. That helper is `readGroupNets(db, group)` in `packages/server/src/ledger/balances.ts`, which #56 moves there unchanged from `functions/ledger/src/routes/balances.ts`. Otherwise `VALIDATION_FAILED` ("Nothing is owed to you in this group") and nothing is sent.
5. **The recipient** is the person the pair's other member resolves to (`mergedInto` followed to the end, as `resolvePerson()` reads it), whatever their member status; the caller never names them. This person is `toPersonId`, the one guarded in step 6 and the activity row's `subjectPersonId`. The address typed, after `normalizeEmail()`, must be an identity whose person resolves to that person (mid-merge, P's identities may still be on P), otherwise `VALIDATION_FAILED`, with a fixed message that never repeats the address. So the route sends "you owe me" only to an address that person is known by: the one they were added with, or, once they have an account, any address they've verified, as for invites ([#374](https://github.com/rojinc/ledgerly/issues/374); the lead on #220). It never picks an address the caller didn't type. A deleted person has no identities left, so a reminder to a former member gets this same answer and doesn't show the deletion. **Every answer with this message is a miss** ([#274](https://github.com/rojinc/ledgerly/issues/274)): a wrong address, no other member, or a recipient whose deletion has started (6.2). Checks are counted first, as for invites ([invites](#invites), step 2, with the shared `ADDRESS_MISS_LIMIT`): a sender at the limit gets `RATE_LIMITED` before the address is checked, each check takes its count under the guard on the sender's row before the address is looked at, and a reminder that's sent takes its count back in step 7's transaction, which already guards the sender's row (only in the window its count was taken in, as for invites).
6. **Guards, then checks, in one database transaction:**
   1. Stage a guard write (a fresh `rev`) on the sender's and the recipient's `persons` rows, as for invites, so parallel requests can't pass a count together.
   2. Read both rows again, and check in this order. A sender with `deletedAt` gets `UNAUTHENTICATED`. A recipient with `deletedAt` (a deletion that started meanwhile) gets the same `VALIDATION_FAILED` as a wrong address, and keeps the count its check took (step 5), so the sender's row never tells the two apart. No second limit check is needed here, as for invites (step 3.1). One way of counting serves every route. A recipient with `mergedInto` (a merge's step 1 that committed meanwhile) gets `CONFLICT`, as does one whose step 1 commits after the guards (it fails this commit), so the app's retry resolves to the person they became, and no reminder or activity row names the placeholder after the merge has moved its rows. It keeps the count its check took, as any refusal after the check does ([invites](#invites), step 2).
   3. **Rate limits** (`REMINDER_LIMITS`, rolling): at most 1 per sender per group in the last 3 days, 3 per recipient person in the last 7 days from all senders, and 20 per sender in the last 24 hours across groups. Otherwise `RATE_LIMITED`, one message for all three.
7. **Stage and commit:** the `reminders` row (ID `id`, `channel: 'email'`, `sentAt` now) and a `reminder.sent` [activity](data-model.md#activity) row: `actorPersonId` = the sender, `subjectPersonId` = the recipient, summary `was sent a reminder` (the feed shows "<subject> was sent a reminder"), no `changesJson`. **Commit before sending,** so N parallel requests with different `id`s can't all count 0 and all send: the guards fail every commit but one.
8. **Send** through Resend with the idempotency key `person-reminder-<id>`. A failed send answers `INTERNAL` and still counts toward the limits, as for invites; the sender's next press retries with the same `id` (step 3), and the same key stops a second delivery. On a re-send, Resend's `invalid_idempotent_request` means the key was used already, with other content: the reminder counts as sent (200). `concurrent_idempotent_requests` means a parallel call is still sending it and may yet fail, so it answers `INTERNAL`.
9. **The email:**
   - **Subject:** "You have a payment reminder", fixed: the sender's name is free text they chose, so it stays out of the subject.
   - **Body:** "{sender} sent you a reminder that you owe them {amount}." and "If you've already paid, let them know so they can record it.", and one link to the app (`APP_URL`).
   - `{sender}` is the sender's `members.displayName` in that group, put on one line (each run of spaces and line breaks becomes one space), with its bidi control characters removed (Unicode's `Bidi_Control` characters: U+202A–U+202E, U+2066–U+2069, U+200E, U+200F and U+061C, which could make the text around it read in another order; the zero-width joiner stays, since emoji need it) and other control characters that aren't whitespace (`oneLine()`, [validation](functions-api.md#validation)), cut to 40 characters as people see them, so an emoji isn't split (with "…"), and HTML-escaped. `{amount}` is the whole balance in the group's currency.
   - **Nothing else:** no recipient or group name (both are what the sender calls them), no transactions, no note (a phishing risk) and no `replyTo` (it would show the sender's account email).

The response and the email are the same whether the recipient is a placeholder without an account, one with an account, or a joined member. The address typed and the amount are stored nowhere, and logs hold IDs and error codes only.

**Accepted risks:**
- Hitting the recipient limit tells the sender that someone else reminded that person this week.
- Whether a typed address matches tells the sender which address the person is known by. Wrong ones are counted: 10 per 24 hours per sender, shared with invites ([invites](#invites), step 2, #274). It only answers for the one person the sender shares a pair group with. As for invites, a match on an address other than the one they were added with shows they have an account: a registered person holds every key they verified. The count limits the guesses; accepted (the lead on #220 and #374). As for invites, each check is counted before the address is looked at, so a burst can't pass the limit. A retry with the same `id` (step 3) answers the same `{ sentAt }` whatever address it carries, but it takes longer when the address matches, since only then is the email sent again. So a retry's check is counted first too, and at the limit, or when its counting conflicts twice, a retry checks no address and sends nothing. A retry never takes its count back, so neither its timing nor the sender's own count tests more addresses than the limit allows.
- **A sender at the limit whose first send failed** (`INTERNAL`) gets the stored `{ sentAt }` from the app's retry, but nothing is sent until the window ends. Since a retry never takes its count back, each press of Send after a failed send costs 1, so during an outage of the email provider about 10 presses lock the sender out of invites and reminders for up to 24 hours. Accepted for v1 (the lead's reviewer on #369): a take-back on a provider failure would bring back the oracle, because a send is tried only when the address matched. The app never retries a failed send by itself: it shows step 8's message ("We couldn’t send the reminder. Try again later."), and only the sender's own press of Send tries again.
- **The sender's name is free text** in the body, up to 40 characters: enough for a short misleading phrase, not a message. Invites have the same exposure, for two names ([invites](#invites)).
- **One inbox can be several persons** (`a+1@x`, `a+2@x`): each has its own recipient limit. Accepted.
- **Retention:** `reminders` rows hold person and group IDs only, and are kept until either person's account is deleted (or a purge). Pruning old rows is a later follow-up.

## Password notice

When an account's password is set for the first time or changed, the account's verified email gets a notice, so a stolen session that sets a password is noticed ([#236](https://github.com/rojinc/ledgerly/issues/236)). It goes with the 24-hour [deletion refusal](#refusals).

The `identity` function subscribes to two Appwrite events: `users.*.update.password` (a password set or changed while signed in) and `users.*.recovery.*.update` (a [recovery](https://github.com/rojinc/ledgerly/issues/290) reset). A reset fires only the second, and Appwrite matches event names exactly (Appwrite 1.8.1, `account.php` and `Workers/Functions.php`). **It never subscribes to `users.*.recovery.*.create`, `users.*.recovery.*` or `users.*`:** the create event's payload carries the recovery secret in plain text. Appwrite runs it as `POST /`, an [event run](permissions.md#function-side-checks), with the event's name in `x-appwrite-event` and the user (or, for a reset, the spent token) as the body:

1. **Who:** a signed-in call gets `FORBIDDEN`. Any other call without a JWT gets `UNAUTHENTICATED` before the route, as for a missing JWT.
2. **The user:** it takes only the user ID, from the event's name (`users.<userId>.…`, the whole name matched as the [change notice](#email-and-phone-change-notice)'s step 1 says); a missing or any other name gets `FORBIDDEN`. Then it reads the user again with `users.get`. It trusts nothing else in the body, and never logs or stores it. Reading the ID from the name also fits a recovery event, whose body is a token, not a user.
3. **When it sends:** only if the user still exists, `passwordUpdate` is under 60 minutes old (`PASSWORD_NOTICE_WINDOW_MINUTES`), and the account email is verified. Otherwise it sends nothing.
4. **The email** goes to that verified address, through Resend with the idempotency key `password-notice-<SHA-256 hex of "<userId>:<passwordUpdate>">`, so each change sends at most one email.
   - It says when the change happened, in the profile's time zone (UTC with no profile), and "If this wasn't you, reset your password now", with a link to the app's sign-in page (`APP_URL`).
   - It holds no password, token, or link that signs anyone in.
5. **Logs** hold the user ID and the outcome only (`logProblem`'s `password_notice`): `sent`, `stale`, `unverified`, `gone`, or `failed` with the email error's type and status.

A forged or replayed call can do nothing new: at worst it asks again, within the hour, for the email the real event already sent, and Resend's key drops that copy. **Accepted:**
- A phone-only account gets no notice until SMS can carry it (#175).
- Other sessions are signed out only for a change through the password route, by the project's session invalidation setting ([environments](../engineering/environments-and-deploys.md#environments)). A recovery reset leaves them signed in, so the sign-in after a reset signs them out ([password recovery](#password-recovery)).
- A notice when the email or phone changes is the [email and phone change notice](#email-and-phone-change-notice).
- **A first password set through an email or phone change.** Appwrite may set a first password through an email or phone change on an account that has none (made with an email code). That fires `users.*.update.email` or `.phone`, so the [email and phone change notice](#email-and-phone-change-notice) covers that path; the 24-hour deletion refusal holds either way, since `passwordUpdate` is set.
- A send that fails (a Resend outage, say) isn't retried: Appwrite doesn't run an event again. The run logs `failed`.
- After the deploy, the lead checks on `ledgerly-dev` that setting a first password fires `users.<id>.update.password` and a recovery reset fires `users.<id>.recovery.<tokenId>.update`, each with the user ID in `x-appwrite-event`.

## Password recovery

Someone who forgot their password, or whose password someone else set, resets it from **Forgot your password?** on the log-in page ([#290](https://github.com/rojinc/ledgerly/issues/290)). It's Appwrite's own recovery, called from the web app.

1. **`/recover`** asks for an email and calls `account.createRecovery({ email, url })`, where `url` is `<origin>/recover/complete` with no query string. Appwrite emails a link to it with `userId`, `secret` and `expire` added, through the project's SMTP (Resend), in its own template. The link works for **1 hour**, and **once**. Appwrite allows 10 requests an hour for each address and each IP, and the URL's host must be a registered web platform.
2. **`/recover/complete`** reads `userId` and `secret`, then replaces the URL with `history.replaceState`. That takes the secret out of the address bar and the Back/Forward history; the browser's own history and the host's access log can still hold the full URL, which is why the link working once, for 1 hour, matters. A reload then finds no parameters, and the page says the link is incomplete. It asks for the new password twice, with Profile's limits (8–256 characters) and refusal messages, and calls `account.updateRecovery({ userId, secret, password })`. A dead link, `user_invalid_token` (used or expired) or `user_not_found` (the account was deleted since), says "This link has expired or was already used." and links back to `/recover`. In case the reset itself went through (say its reply was lost and the form was sent again), it also links to `/login?reset=1`. The secret is never logged, and is dropped once the link is used up.
3. **What a reset does:**
   - It sets `passwordUpdate`, so the 24-hour deletion [refusal](#refusals) starts. That's intended: whoever reset it may not be the owner.
   - It marks the email **verified**, since opening the link proves control of the inbox.
   - It creates no session, and **deletes none**, whatever the project's `invalidateSessions` setting says. So a session someone else holds stays signed in.
4. **This browser is signed out first.** A browser still signed in when the link is used would be sent past `/login` into the app, missing the sign-in below. So after a reset the page signs it out (`account.deleteSession({ sessionId: 'current' })`; a 401 means nobody was signed in) and drops the cached data, as logging out does. If that fails, it says so and offers **Try again**; the form doesn't come back, since the link is used up.
5. **Signing in afterwards signs out the other sessions.** The app then goes to `/login?reset=1` ("Password changed. Sign in to finish."). Signing in from there, with the password or an email code, signs out every **other** session with the helper Profile's **Sign out other devices** uses: `account.listSessions()`, then `account.deleteSession()` for each one that isn't `current`, where a 404 (gone already) counts as done. Never `account.deleteSessions()`, which on Appwrite 1.8.1 deletes the current session too. If that fails, the page says so and offers **Try again** before the app opens.

**Accepted risk:** `createRecovery` answers `user_not_found` (404) for an address with no account and `user_blocked` (401) for a blocked one (for example, mid-deletion), so the API shows whether an account exists, as sign-up already does. The page shows the same message for both and for a sent link: "If that address has an account, we've sent a link. It works for 1 hour."

## Email and phone change notice

When an account's email or phone number changes, a notice goes out by email, so a stolen session that moves the account to someone else's address or number is noticed ([#268](https://github.com/rojinc/ledgerly/issues/268)). It uses the [password notice](#password-notice)'s event route.

`identity` also subscribes to `users.*.update.email` and `users.*.update.phone`. Each runs `POST /` as an [event run](permissions.md#function-side-checks):

1. **Which event:** the route matches the whole name in `x-appwrite-event`: `users.<userId>.update.password` or `users.<userId>.recovery.<tokenId>.update` (the [password notice](#password-notice)), `users.<userId>.update.email` or `users.<userId>.update.phone`, where `<userId>` is everything between `users.` and that ending (an Appwrite user ID can contain `.`; a recovery `<tokenId>` can't, so the match is unambiguous). For the two change events the ID must also equal the body's `$id`: otherwise nothing is sent, the run logs `mismatch` and answers `{}`. The body's `$id` is used for nothing else. An event run with a missing or any other name gets `FORBIDDEN`. A signed-in call gets `FORBIDDEN`, as for the password notice.
2. **The user:** the route reads it again with `users.get`, and takes nothing else from the event: not the old or new value, even if the payload holds one. It stores nothing about the change itself, only the pending sends of step 6: a [`changeNotices`](data-model.md#changenotices) row each, at most 3 per user, with no address or number ([#345](https://github.com/rojinc/ledgerly/issues/345)). Checks run in this order, each one ending the run:
   - the user is gone, or their person has `deletedAt` (`gone`), so a deletion under way changes nothing here;
   - then, for an email change, the old addresses (step 3); for a phone change, the account's verified email (step 4).
3. **An email change** notifies the **old** addresses, which come from our own `identities`, never from the event: every identity on the user's person with `type = email` and `verified = true` whose key isn't `identityKey('email', <the account's current email>)`, with no cap (the lead's call, #314): each is an inbox this account verified, and each gets one key per change. They're sent newest `verifiedAt` first (a row with none counts as oldest; equal ones by `$id`), each its own email under its own key. Claim never deletes a verified key and keeps its first `verifiedAt`, so those rows are still there after the change. With no person, or no such identity (the old email was never verified), nothing is sent (`no_old_address`). If the current email is empty, or `identityKey()` throws on it, no key is left out.
   - **The email** says the account's email was changed to the new address, masked as `j***@example.com`: the first character of the account's email as Appwrite holds it, `***`, then `@` and its domain, HTML-escaped.
   - **Key:** `email-change-notice-<SHA-256 hex of "<userId>:<that old key>:<the user's $updatedAt>">`. A new change gets a new key, so a change undone and made again is noticed again.
4. **A phone change** notifies the account's **current verified email** (`emailVerification`), not the old number: SMS needs [#175](https://github.com/rojinc/ledgerly/issues/175). It's sent with no person beyond the `deletedAt` check, but its row needs one (step 6). With no verified email, nothing is sent (`unverified`).
   - **The email** says the account's phone number was changed to a number ending in its last 3 digits (`…678`), or that it was removed if the account has none now.
   - **Key:** `phone-change-notice-<SHA-256 hex of "<userId>:<the user's $updatedAt>">`. The number isn't in it.
5. **Both emails** have a fixed subject that holds no address or number. They say "If this wasn't you, write to `<SUPPORT_EMAIL>` from this address right away", with the address as escaped plain text, not a link, or "reply to this email" when the `SUPPORT_EMAIL` variable isn't set. They have one link, the app's sign-in page (`APP_URL`), and no token or link that signs anyone in. Recovering an account someone else has taken over is [#290](https://github.com/rojinc/ledgerly/issues/290).
6. **Each address is tried, whatever happened to the others, unless every send would fail (below), and kept until it's sent** ([#345](https://github.com/rojinc/ledgerly/issues/345)).
   - **Rows first:** before the first send, one database transaction keeps a [`changeNotices`](data-model.md#changenotices) row for each email, **at most 3 per user**, counting the rows already there, so one account can put at most 3 sends ahead of anyone else's in step 8's queue (the lead on [#462](https://github.com/rojinc/ledgerly/pull/462)).
     - **A row** holds the user ID, which notice, the email's key, and the `identities` row ID of the address it goes to: an email notice's old address, or, for a phone notice, the identity on the user's person whose key is `identityKey('email', <the verified email of step 4>)`. It holds no address or number.
     - **The cap holds across runs:** the transaction stages a guard write on the user's person (a fresh `rev`) first, then lists the user's rows as committed (`idx_userId`), so two runs for one user never both pass it. A 409 runs it once more.
     - **A replayed event's row,** one already there with the same key, is kept as it is and counts once.
     - **No row:** the emails past the cap, in the order they're sent, and a phone notice whose email has no such verified identity (or whose user has no person, or whose email `identityKey()` refuses), are sent now but never retried. With no row to write, there's no transaction. The run logs them as `dropped`, with how many (`count`).
     - **If the rows can't be written,** a second 409 included, the run logs `failed` with the cause `queue`, and sends anyway, with nothing kept to retry. The person's `rev` also guards merges, claims, invites and reminders, so one of those at the same moment can cost a notice its retry.
   - **Sending:** the sends go one after another, at least 500 ms apart, so the run doesn't rate-limit itself (Resend allows 2 a second). Resend's answer for a key it has seen (`invalid_idempotent_request`, or `concurrent_idempotent_requests` from a run sending the same notice at that moment) counts as sent. A `rate_limit_exceeded` is tried once more with the same key, after Resend's `retry-after`, if that send can still start by 12 s (below).
   - **After each send:** an email that's sent has its row deleted, and so does one Resend refuses for good (`validation_error` with 400 or 422), which is logged `failed`. A failure every send would meet (`sendingBlocked()`: a 401 or 403, a `validation_error` among them, an invalid key or a missing setting, [conventions](../engineering/conventions.md#functions)) is ours, not the address's: every other address would fail the same way, so the run stops there, logs it once and fails, and the rows left stay for step 8 ([#469](https://github.com/rojinc/ledgerly/issues/469)). Any other failed send keeps its row and is logged `failed`, and the run goes on to the next address, then fails after the last one.
   - **The budget:** no send starts after 12 s of the run, inside identity's 15 s timeout, and each send's own timeout is cut to what's left of 14 s. The addresses left then keep their rows, are logged as one `failed` with the cause `budget` and how many (`count`), and the run fails, so a long list or a slow Resend never ends the run without a trace.
   - Appwrite doesn't run an event again; identity's hourly run tries the rows again (step 8).
7. **Logs** hold the user ID, which notice (`email` or `phone`) and the outcome only (`logProblem`'s `change_notice`, the notice as `identityType`): `sent`, `gone`, `no_old_address`, `unverified`, `mismatch` (a warning), or `failed` (an error) with the email error's type and status (any other error's class), or the cause `budget` and how many were left, or the cause `queue`; or `dropped` (a warning) with how many emails got no row (step 6). A retry (step 8) logs `retried`, `expired` (a warning), `gone` or `failed`, each with the row's `attempts`.
8. **Retries** ([#345](https://github.com/rojinc/ledgerly/issues/345)): identity's hourly `POST /` run, after it carries on merges ([finishing merges](#finishing-merges)), takes the `changeNotices` rows oldest first (`$createdAt`), only those written more than 15 seconds ago, identity's timeout, so it never sends beside the event run that wrote them. It works within step 6's limits, counted from the run's start: no send starts after 12 s, sends are at least 500 ms apart, and each send's timeout is cut to what's left of 14 s, so the merges' 9 s are never cut short. Rows it doesn't reach wait for the next hour. For each row:
   - **23 hours after its key was made:** the event run made the key when it wrote the row, so that's 23 hours after the row's `$createdAt`. From then on the row is deleted unsent by the first run that reaches it, normally the first, and logged `expired`. The check comes before every send, so a notice is never sent more than 23 hours after its key was made: Resend keeps a key 24 hours, so a later send could deliver it twice. A replayed event writes its row again once the first was sent and deleted, so its 23 hours count from the replay; a late retry of it is the replay case under **Accepted**.
   - **The email is built again** from `users.get` and the row's identity, which is the address it goes to, for a phone notice too. It checks only the user, their person and the identity, so step 4's `emailVerification` check and step 3's skip of the current email's key don't apply. If the account's email has changed since, a phone notice still goes to the address it was first meant for, so a retry never tells the person who changed both the phone and the email instead of the owner (the lead on [#462](https://github.com/rojinc/ledgerly/pull/462)). It shows the account's email or phone as they are now, masked as in steps 3 and 4. When there's nothing to send, the row is deleted unsent and logged `gone`: the user is gone or their person deleted, or the identity is gone, on another person or no longer verified.
   - **It's sent with the row's own key**, never one built again, since the user's `$updatedAt` may have changed since.
     - Sent, or a key Resend has seen: the row is deleted, logged `retried`.
     - Refused for good (`validation_error` with 400 or 422): deleted, logged `failed`. A failure every send would meet (`sendingBlocked()`) is ours: as for a 429, it ends the retries for the run, logged once, with no row changed ([#469](https://github.com/rojinc/ledgerly/issues/469)).
     - A `rate_limit_exceeded`: logged `failed`, with `attempts` left as it is, and the retries end for that run, since the limit is shared. Unlike step 6, it isn't tried again after `retry-after`.
     - Anything else: `attempts` + 1, logged `failed`, and the next row is tried.

   The run's answer counts them by outcome: `notices: { retried, failed, expired, gone }` (the lead on [#462](https://github.com/rojinc/ledgerly/pull/462)). `dropped` is only the event run's (step 6).

**With the password notice:** an account with no password that changes its email or phone may get a first password from Appwrite. If that fires only this event, this notice is the one that covers it ([accepted](#password-notice)). If it fires `update.password` too, after an email change the password notice finds the new email unverified and sends nothing; after a phone change the email is still verified, so the user gets both notices. Accepted.

**Accepted:**
- An old address that's the attacker's, verified on the way (A → B, B verified, then B → C), gets a notice too. The rule sends to every old verified address so that the owner's is among them.
- An `update.email` event with no real change notifies the other verified addresses that the email "was changed to" the current one, masked.
- A replayed event after Resend's 24-hour key has expired sends the same notice again. Only Appwrite makes an event run ([permissions](permissions.md#function-side-checks)), so that's a replay of a real change.
- A phone change on an account with no verified email gets no notice until SMS can carry one (#175). The SMS notice to the old number is a follow-up after #175.
- The new address's domain is text the person who changed it chose, and a mail client may turn the masked address into a link. Accepted, as for a reminder's sender name.
- An old address may no longer be the user's (a work address given up, then reissued to someone else). It still gets the notice, with the new address masked.
- Mid-merge, an old key can still be on a person being merged into the user's (step 3 of [merging](#merging-two-persons) moves identities last), so it isn't notified.
- **A notice still unsent 23 hours after its key was made is dropped** ([#345](https://github.com/rojinc/ledgerly/issues/345)). The app's other emails (reminders, invites, statements) share Resend's limit of 2 a second. The retry sends about 24 rows a run, oldest first, or about 6 when the merges take their 9 s, so 23 runs reach about 550 rows (about 140 with the merges' 9 s every hour).
  - **One account** keeps at most 3 rows, so it can put at most 3 sends ahead of another account's notice.
  - **Many accounts** can put more: N accounts that each keep 3 rows put 3N sends ahead. Each needs a verified email, and its own sends failing at the time, or its rows go once they're sent. About 185 such accounts (about 46) make a notice behind them expire unsent. Accepted (the lead on [#462](https://github.com/rojinc/ledgerly/pull/462)).
  - **These figures assume each row ahead goes on its first retry.** A row whose retries keep failing (a 5xx or a timeout) keeps its place and is tried first every hour, so about 24 of them (about 6) hold back every newer notice until they expire. A 429 ends that hour's retries, and the scheduler's [step 3b](scheduling.md#step-3b-transaction-change-emails) sends at the full 2 a second, maybe in the same minute. So a Resend outage, or a busy hour, slows the retries further.
  - **No retry at all:** a notice whose rows couldn't be written; an email past its account's cap, which counts rows an event run is still sending (an email change with 3 old addresses, then at once a phone change, leaves the phone notice with none); and a phone notice whose email has no verified identity.
  - Either way, only a `change_notice` log line shows it. Security notices don't go ahead of other emails under the shared limit (the lead on #345).

**Dev checks, by the lead after the deploy:**
- an email change and a phone change each fire their event, with the user ID in `x-appwrite-event`;
- `emailVerification` is false right after an email change (the password notice relies on it, above);
- whether an account with no password also fires `update.password`;
- whether a user ID with a `.` is accepted at sign-up (step 1 handles it either way).
- the runs log `sent`, not `mismatch`: the event body's `$id` is the user's ID.

## Deleting an account (M4)

`account POST /delete` ([functions API](functions-api.md#account)), from the delete screen ([#50](https://github.com/rojinc/ledgerly/issues/50)). Deletion has its own function, `account`, so `identity` (which runs bootstrap for every new user) never holds `users.write` or file access. **Deleting means anonymising.** Shares, statements and balances point at the person ([I-3](ledger.md#invariants)), so the `persons` row stays: `deletedAt` set, `userId` cleared, `displayName` "Former member", and no permissions. It keeps `claimedAt` and the address-miss count and its start: times and a count only ([#535](https://github.com/rojinc/ledgerly/issues/535)). Their identities, profile (business details included), the invites and reminders they sent or were sent, and the Appwrite user are deleted ([step 5](#order) has the full list). There is no undo or grace period in v1: typing DELETE is the confirmation.

### Each group they joined

For every group where they have an `active` or `left` member row, its team decides:

- **Purge, if nobody else is in the team.** This is always true of the personal group. It sets `archivedAt` (as the keep's archive does, below) and then deletes the team, first, so jobs and writes stop; a crash between the two leaves the team, which a rerun decides from again. Then it [purges the group](#purging-a-group), deleting their own member row last.
- **Keep, otherwise.** In one transaction, with a fresh group `rev`: their member row becomes "Former member", `left` and `viewer`, with `leftOn` set as leaving sets it (today in the group's time zone, or `joinedOn` if that's later) if it's empty, so `days` bills stop counting them; and a `member.left` activity row by them, with `subjectPersonId` = their person and no name, so the row counts as leaving on their own ([leaving](permissions.md#leaving-a-group)). Then, in this order: **the schedules**, whether or not the group is archived ([#428](https://github.com/rojinc/ledgerly/issues/428): an unarchive must find no occurrence made before the deletion still naming them; `endScheduleOn()` doesn't refuse an archived group, only the route does), in the group that they created, or whose template names them (`everyPersonId()`), and in a kept `pair` or `employer` group every schedule made before the deletion (its `$createdAt` no later than their `deletedAt`, so a rerun decides as the first run did), end on the earlier of their stored end and today, as `POST /schedules/{id}/end` does (occurrences after it that can still change are removed, so these schedules make no new occurrence naming them; both use `endScheduleOn()` in `packages/server/src/scheduler/end-schedule.ts`). A paused one is ended the same way, by its stored `endsOn` and not its pause, and keeps `pausedFrom`, so a later resume makes nothing after that end ([pausing](scheduling.md#pausing-a-schedule)). If its pause begins by that end, it's never made up to it, so a rerun ends it again, which changes nothing. One that has already ended by today (by `endsOn`), been made up to its end, and has no occurrence left that an end would remove (`scheduled` or `due`, not edited, dated after its end and from today), is left as it is, so an end cut off before its deletes runs again. One that hasn't started yet (`startsOn` after today) and has no posted occurrence is deleted instead, with its occurrences, as `DELETE /schedules/{id}` does (`deleteScheduleRows()`, which takes their receipts off), rather than ending before it starts. A template that can't be read names nobody, and its schedule ID is logged; **then the handover or the archive**, for a kept group with no joined admin left ([#503](https://github.com/rojinc/ledgerly/issues/503)). A joined admin whose own deletion is under way still counts as one until their own keep. **A house, archived or not, that still has an `active` member** gets that member as its admin instead: the earliest `active` row with `role: 'member'`, by `joinedOn`, then `$createdAt`, then `$id`, and only if there's none, the earliest `active` `viewer` in the same order. A viewer was made read-only on purpose, so a member always wins; but a house whose only `active` people are viewers would otherwise be left with nobody who can manage it. Only an `active` row is picked, never one that moved out or a placeholder that hasn't joined. An `active` member whose own deletion is under way is picked like anyone else (refusal 6 counts them too), and their own deletion then hands over again. One guarded transaction, with a fresh group `rev`, stages that member's row as `admin` and a `member.updated` row by them, naming that member (`subjectPersonId`), with the summary "was made an admin" and `changesJson` `{ before: { role }, after: { role: 'admin' } }`, as `PATCH /groups/{id}/members/{memberId}` writes. It then reads the stored members again, before the commit: if a joined admin appeared meanwhile, or that member is no longer `active`, it rolls back and leaves the group for the next run (so the route answers `finished: false`), which decides again. A join, an archive or another deletion's handover that commits first fails this commit (the group `rev`). A rerun finds the new joined admin and moves on, so it never makes a second one. **Any other such group that isn't archived yet is archived** (with a `group.archived` row by them, as an admin's archive writes): an `employer` or `pair` group, or a house with no `active` member left (everyone else in its team moved out, say) (below); **then leaving the team, last**, so a crash before it leaves the group to be finished, never with its schedules still running.

**A rerun never decides again.** What a group's state says decides how a rerun carries on, never the team as it is by then:

- **The group's team is gone:** a purge was started. From a row without the keep's write, it carries on, and their own member row, deleted last, ends it. A row with the keep's write (the next rule) is done instead: their own deletion only deletes a team it purges, which it never does once it has kept a row, so another purge deleted it, and that purge deletes the kept row with the others. It ends with a row no other purge deletes (another account deletion's own, or a [group delete](#deleting-a-group)'s `deletingBy`), whereas purging from the kept row too would let the two delete each other's end row, fail both last transactions and leave the group row for good (AI A on [#446](https://github.com/rojinc/ledgerly/pull/446)).
- **Their member row shows the keep's own write ("Former member", `left` and `viewer`), with their own `member.left` dated on or after `deletedAt`** (`leftOnTheirOwn()` with `deletedAt` as the earliest date, rather than the member row's `$createdAt`)**:** the keep's transaction is done. The schedule, handover or archive, and team steps are then retried on every run until step 6, even if they're no longer in the team or everyone else has since left it; each is safe to repeat, and a handover that found a joined admin does nothing. A `left` row without the keep's write (their own leave that committed after step 2, or before it with a crash after) still has their name, so it gets the keep. So does a kept row an admin renamed before step 6: the rerun writes "Former member" again, with a second `member.left`. Accepted: it takes a rename inside an unfinished deletion, and costs one activity row ([#535](https://github.com/rojinc/ledgerly/issues/535)).
- Anything else is decided from the team, as above.

**Changes after the checks.** Step 1's checks can be overtaken before a group's turn comes, and a deletion can't be refused after step 2. A kept house this check let through that has no joined admin left at its turn (another admin left meanwhile, or a placeholder joined since) gets one of its `active` members as admin, the handover refusal 6 would have asked them for ([#503](https://github.com/rojinc/ledgerly/issues/503)); so does an archived house, which refusal 6 doesn't check. The handover is the keep step's ([above](#each-group-they-joined)): the earliest `active` `member` by `joinedOn`, then `$createdAt`, then `$id`, or only if there's none the earliest `active` viewer; one guarded transaction with a fresh group `rev`, the role write staged before the checks; re-reading the members after staging, it rolls back and leaves the group for the next run if a joined admin appeared or the picked row is no longer `active`; and a `member.updated` row by them, with the new admin as `subjectPersonId`. Only a house with no `active` member left is archived, like an employer or pair group. The handover waits for nothing: the group stays as it was, so a finalize or a timer goes on as before. A group archived with no joined admin can still be deleted by the last person in its team ([deleting a group](#deleting-a-group)). A group with a statement `finalizing` isn't archived or purged until the finalize ends, or has been stuck for an hour (below), and a kept one with a timer someone else started still running isn't archived until it's stopped or voided (a timer in an archived group can't be): the group is left for the next run. A purge doesn't wait for a timer: nobody else is in the team, and the timer goes with the group's rows.

**A stuck finalize.** A `finalizing` statement that hasn't been written for an hour was left by a crash. It began after step 1 (which refuses one they could finish), and in a group with no joined admin, nobody can resume it. So it isn't waited for: a kept group that would be archived is archived over it ([#503](https://github.com/rojinc/ledgerly/issues/503)), with the statement still `finalizing`, logged as `stuck_finalize_archived` with the group's and statement's IDs, and the deletion carries on; a purge goes ahead, and the statement goes with the group's rows, and any PDF it uploaded with the group's files. Once it's archived, the last person in its team can delete it, and the last person's leave is refused ([deleting a group](#deleting-a-group), [leaving](permissions.md#leaving-a-group)). A divide can still be finished: an admin who joins later (a placeholder added as one) can unarchive the group, which doesn't wait for a finalize, and then resume it, which only an archived group refuses. An invoice can't, once its worker has deleted their account: its finalize is refused (`CONFLICT`, [finalize](statements.md#2-finalize-post-statementsidfinalize)), so it stays `finalizing`, and the group can only be deleted. That holds in a group still managed, too, such as an employer group where the employer was also made admin: that admin's archive goes over such an invoice once the worker's `deletedAt` is more than an hour old, when no finalize run that began before it can still be going, and then the last person in its team can delete the group ([#519](https://github.com/rojinc/ledgerly/issues/519)). A kept house with an `active` member gets its handover instead (above), and the new admin can resume a divide.

Groups where they're a `placeholder` (never joined) are left exactly as they are: changing them would show the other members they had an account ([D-016](decisions.md#d-016-being-added-to-a-group-doesnt-make-you-a-member-you-join)).

### Refusals

Checked in this order, and each changes nothing:

1. **The body isn't `{ confirm: 'DELETE' }`:** `VALIDATION_FAILED`. A caller no person names gets `NOT_FOUND` ("Set up your account first."), as for identity's routes.
2. **The session is old.** The route reads the session ID from the caller's verified JWT and loads that session (`users.listSessions`). If it was created more than 10 minutes ago (`REAUTH_WINDOW_MINUTES`), it answers `FORBIDDEN` with `details: { reason: 'reauth' }`. The app offers **Sign in again**, which signs them out and brings them back to the screen through the sign-in page (password or email code), where they confirm again. So a stolen session that's been open a while can't delete the account. The check fails closed: a JWT with no session ID, or a session that `users.listSessions` doesn't return, gets the same answer.
3. **The password changed recently.** If the user's `passwordUpdate` is less than 24 hours old (`RECENT_PASSWORD_CHANGE_HOURS`), the answer is `FORBIDDEN` with `details: { reason: 'recent_password_change' }`. A stolen session on an account without a password could otherwise set a first one (#203 allows that without an old password), sign in fresh and pass step 2. Appwrite also sets `passwordUpdate` when an account without a password changes its email or phone, so those are caught too. Accepted: a new account that set a password today can't delete it until tomorrow.
4. **A timer they started is running** in a group that isn't archived: `CONFLICT`. They stop or void it first. A timer left in an archived group can't be stopped while the group is archived, and doesn't block deletion ([timer shifts](scheduling.md#timer-shifts)).
5. **A statement is being finalized** in a group where they're the only joined admin: `CONFLICT`. Only an admin can finish a finalize, so they finish it first: once they're gone nobody could, and an hour later the deletion would go on without it ([a stuck finalize](#each-group-they-joined)). An invoice whose issuer has deleted their account doesn't count, since nobody can finish it ([#519](https://github.com/rojinc/ledgerly/issues/519)).
6. **They're the only joined admin of a house that isn't archived and has another `active` member** who could be made admin: `VALIDATION_FAILED` with `details: { groupIds }` (an exception to `details` holding schema issues). They make someone else admin first: the rule leaving uses ([leaving](permissions.md#leaving-a-group)). A kept house with no `active` member left (everyone else in its team moved out, say) is archived instead, as an employer or pair group is. An archived house isn't checked here: at its turn, it gets one of its `active` members as admin, if it has one: a `member` before a `viewer`, the earliest joined first, by the keep step's guarded handover ([changes after the checks](#each-group-they-joined)). So does a house this check let through that has no joined admin left at its turn (another admin left meanwhile, or a placeholder joined since) ([changes after the checks](#each-group-they-joined), [#503](https://github.com/rojinc/ledgerly/issues/503)). A house with nobody else in its team is purged, as above.

Non-zero balances don't block it; the delete screen warns about them.

### Order

1. The refusal checks.
2. Set `persons.deletedAt` and `displayName` "Former member", with a fresh `rev` (a [guard write](ledger.md#concurrency)). **This is the point of no return:** from here every step runs to the end, and none is undone. A call after this skips the checks (apart from the body) and carries on.
3. Label the Appwrite user `deleted` (`users.updateLabels`), block them and delete their sessions, so an old JWT fails `account.get()` (`UNAUTHENTICATED`). A 404 counts as done.
4. The groups, one at a time, as above.
5. Only once **every** group is done: delete their identities, the identities of any person still being merged into them (`mergedInto` = theirs, `idx_mergedInto`: a merge moves identities last, so an unfinished one leaves their verified key there), the invites they sent, the invites sent to their member rows in groups they joined (each holds the address it went to; one to a group where they're a placeholder stays, as the group does, until [scheduler step 5b](scheduling.md#step-5b-invite-clean-up) deletes it), the reminders they sent or were sent, a person still being merged into them included (`idx_sentBy_sentAt`, `idx_toPerson_sentAt`), and their profile. Their `active` and `left` member rows are listed once more first: a row that a join or a new group committed after step 4 listed them waits for the next run.
6. Clear `persons.userId` and the row's `read("user:<userId>")` permission.
7. Delete the Appwrite user (a 404 counts as done).

Step 6 comes before step 7 because Appwrite user IDs are chosen by the client at sign-up: once the user is deleted, someone who knows the ID could sign up with it, and must not find a person to bootstrap into. For the same reason, **a person with `deletedAt` is never resolved from a `userId`** (bootstrap, claim, join, `PATCH /profile` and `requireMember()` skip it, as if there were no person). Claim's identity writes, join's writes and the name `PATCH /profile` writes also stage a [guard write](ledger.md#concurrency) on the person and check `deletedAt` again, so a deletion that passes step 2 after the lookup gets nothing written for it: the profile stays until step 5, and a name written after step 2 would replace "Former member" for good ([#535](https://github.com/rojinc/ledgerly/issues/535)). So `/bootstrap` refuses with `UNAUTHENTICATED`, writing nothing, a user labelled `deleted` (checked again after it stages its writes) or one with a person whose `deletedAt` is set, and step 7 first looks up persons by `userId` once more: a person without `deletedAt` there (made by a bootstrap that committed after step 2) is purged before the Appwrite user is deleted.

Every step can be repeated: a crash after any of them, then a rerun, leaves the same rows. The route works for up to 20 seconds and returns `{ deletedAt, finished }`. The hourly job (`account POST /`, scheduled only) finishes any person with `deletedAt` set and `userId` still set (`persons.idx_deletedAt`), and deletes any Appwrite user labelled `deleted` whose person no longer names it. It skips deletions started in the last minute, which the route may still be running. For a labelled user it runs step 7 as the route does, purging first any person without `deletedAt` that still names it, and it dates the deletion by the user's `$updatedAt`, which is never earlier than step 3's label. This is the job's account pass; its group pass comes after it ([finishing purges](#finishing-purges)).

### What is kept, and why

- **Final statements, their snapshots and PDFs in kept groups,** as issued, ABN and bank details included: other members already hold these documents ([D-010](decisions.md#d-010-closed-periods-never-change)). Merges don't rewrite them either.
- **Receipts on kept transactions, and text other people typed** (descriptions, notes, void reasons).
- **Groups they left on their own:** their member row is renamed "Former member"; their shares and history stay, like any kept group's. They aren't in `my-records.csv`, since the user can no longer read those groups: export gap, accepted for v1.
- **Receipts they uploaded but never attached** keep their own permissions until the scheduler's clean-up deletes them, about 24 hours after upload ([step 5](scheduling.md#step-5-receipt-clean-up)).
- **Activity rows already written,** with the text they were written with. New member and group rows name no one: their summaries and `changesJson` hold no display name, and `subjectPersonId` points at the member's person, so the app shows the current name ("Former member" after deletion) without rewriting rows ([activity](data-model.md#activity)). Activity is deleted only with a purged group.

A purged group's invoices go with it, so the delete screen tells users to export first ([data export](security-and-privacy.md#data-export)). Appwrite's backups keep deleted data for their own retention period ([retention](security-and-privacy.md#retention)).

### After deletion

- **Signing up again** with the same email makes a new person. The old one is never linked back: its identities are gone, `isPlaceholder()` skips persons with `deletedAt`, and no `userId` resolves to it. Claim and join skip a group whose team is gone, a merge puts such a group off until its rows are gone, and a merge into a deleted person is never continued.
- **No new record names a deleted person where they had joined.** This applies in a group where their member row isn't `placeholder` (in practice the kept groups).
  - **The ledger refuses a write that would name them anew** ([functions API](functions-api.md#ledger), "Deleted people"): as a payer (one the server fills in included), in its split or the default split, in an item, or as one of a shift's two people.
  - **A record made before the deletion** keeps everyone it already named or gave a share, also through its default split or as a shift's employer. So it can still be corrected, posted and voided, and a timer can still be stopped.
  - **The scheduler** refuses a template whose trial occurrence would name them, and an edit of a schedule they created. Step 2 doesn't post an expense or bill they would pay as its schedule's creator ([scheduling](scheduling.md#step-2-auto-post)).
  - **Still allowed:** payments and adjustments that name them, so balances with a former member can still be settled.
  - **Who, not how much:** an edit can still change what someone already on a record pays or owes, as it can for any member.
  - Where they never joined, nothing changes, so the refusal can't show the deletion (D-016).
  - **Schedules left running:** in a kept house, a schedule they didn't create, and whose template doesn't name them (`everyPersonId()`), keeps running. A template has no billing period, so its occurrences split by date, and the default split leaves them out after their `leftOn`. So only an occurrence made after the deletion and dated on or before their `leftOn` (the deletion day, usually) can give them a share. It's refused when posted, until an edit splits it between the others, and step 2 counts it as failed.
- Accepted risk: with their identities deleted, adding that email to a group again makes a new placeholder instead of answering `CONFLICT`, and an invite to it goes to whoever holds the address now. An invite to their *old* placeholder row (in a group they never joined) with that email gets `VALIDATION_FAILED`, since the row's person is deleted.

## Purging a group

A purge deletes a group nobody else is in, with everything in it. Two things start one, and both have archived the group and deleted its team first, so jobs and writes stop:

- **An account deletion,** for each group they joined that nobody else is in ([each group they joined](#each-group-they-joined)). Their own member row ends the purge.
- **A group delete,** by the last person in an archived group ([below](#deleting-a-group)). The member row of `deletingBy`, who started it, ends the purge.

The row that ends the purge is deleted last, with the group row. A rerun ends with the same row, and so does the same person's account deletion purging the group, so two purges by one person never delete each other's last row.

Its statements' PDFs go first, then its rows, in batches of at most 90 writes, each also giving the group row a fresh `rev` as every writer of shares does ([concurrency](ledger.md#concurrency)), so a [nightly check](scheduling.md#step-6-nightly-check) reading the group meanwhile sees it change and doesn't rebuild its `balances` row (each transaction with its shares and items, and its receipts taken off ([receiptFiles](data-model.md#receiptfiles)), their files deleted just before its batch, so a run that stops keeps what it has done, and the next looks at one of those files again only where another of the group's transactions lists it, and finds it gone; a crash in between leaves a row naming a gone file, which the next run counts as done, member rows after all shares, and after a last pass by `idx_group_person_date` for any share whose transaction is gone, the group's `balances` row with the first batch, and its `reminders` rows, found by `idx_groupId`, in batches too, and every invite to one of its member rows, whoever sent it, found by `memberId` before those rows go: no index, so Appwrite reads the small table, as step 5 does), then for any placeholder left with no member row anywhere, `orphanedAt` = now, so [scheduler step 5c](scheduling.md#step-5c-placeholder-clean-up) deletes its identities, the invites to them and its name 30 days later, as after a removal: deleting them at once would let an account or group made to be deleted test which addresses are known (the lead on [#367](https://github.com/rojinc/ledgerly/pull/367)). A placeholder's `orphanedAt` is staged in the same transaction as its member row in the group, so a crash never leaves one unmarked that a rerun can't find, and the group row goes with the member row that ends the purge. Another person's `active` or `left` member row without the keep's write is left alone while their own deletion is under way (`deletedAt` set, `userId` not yet cleared): their purge of the group deletes it last, so two deletions purging one group at once never delete each other's row and fail each other's last transaction. A file is deleted only when its permissions are exactly `read("team:<the purged group>")` and its [`receiptFiles`](data-model.md#receiptfiles) row lists the transaction and none outside the purged group (the transactions it lists are read by ID), so a file shared with another group's transaction stays. A file with no row (attached before the ledger kept them, until the backfill has run) counts as listed elsewhere and stays. A statement's PDF is looked for under its `pdfFileId`, or under the statement's ID when that's empty: finalize uploads it under that ID before it sets `pdfFileId`. The purge never deletes `receiptFiles` rows itself: taking the receipts off leaves the rows of the files it deleted detached, and scheduler step 5 deletes those rows about 25 hours later (their files already gone, so they count as skipped). A placeholder is marked only after a staged write, and only if, re-checked after it, `isPlaceholder()` still says so (a merged person is kept) and it still has no member row. Deleting any member row of a placeholder stages a write on its person too (a fresh `rev`, with `orphanedAt` when it keeps no other row) and re-checks, so two purges deleting its last two rows at once fail one commit rather than leave it unmarked. Accepted: when a placeholder joins (by a claim or an accepted invite), or a [merge](#merging-two-persons)'s step 2 adds U to the team and then repoints P's member row, after the team is read and before it's deleted (an account deletion's archive transaction falls in between), the join succeeds, but the joined person's member row and team membership go with the group, which then reads as deleted. A group delete has no such window: its step 2 lists the team again after staging, and a join or merge checks `deletingAt` in its own guarded transaction, so the two never both commit ([deleting a group](#deleting-a-group); AI E on [#446](https://github.com/rojinc/ledgerly/pull/446)).

### Deleting a group

The last person in an archived group can delete it, with everything in it ([#429](https://github.com/rojinc/ledgerly/issues/429)): `account POST /groups/{id}/delete` ([functions API](functions-api.md#account)). It is the purge above, so it adds no new kind of retention, and a group anyone else is still in can't be deleted: that is what lets its final statements go with it. Usually the caller is an admin. **Once the group has no joined admin, anyone in it can delete it, whatever their role** ([#486](https://github.com/rojinc/ledgerly/issues/486)): an `active` member or viewer, or someone who moved out and is still in the team. Only an account deletion leaves a group so: an employer group whose worker deleted their account, with the employer joined as a viewer, say. It archives the group, even over a stuck finalize, and without this rule nobody could delete it or unarchive it unless an admin placeholder joins it, and the employer couldn't even leave it. A house, archived or not, that still has an `active` member isn't left so: one of them is made its admin instead, a `member` before a `viewer`, the earliest joined first ([each group they joined](#each-group-they-joined), [#503](https://github.com/rojinc/ledgerly/issues/503)). Unarchive stays admin-only: a group with no admin couldn't change its settings, finalize statements or add an admin. In the app, the admin of an archived group where no other member is `active`, and anyone in an archived group with no joined admin where nobody else is `active`, gets **Delete group**, the latter with a line saying the group has no admin (the app can't see the team itself, so someone who moved out, and is still in it, gets the `shared` refusal), which links to Export first, as the account delete screen does, and asks them to type DELETE. There is no undo.

1. The refusal checks ([functions API](functions-api.md#account)); each changes nothing.
2. One database transaction stages `deletingAt` = now and `deletingBy` = their person on the group row, with a fresh `rev` (a [guard write](ledger.md#concurrency)), then reads the stored group again: one unarchived meanwhile is refused as in step 1, and one whose delete another call has started carries on with that one. It also lists the team again, after the staging: if anyone else is in it by now (a join adds itself to the team first), it refuses `shared` as in step 1, having written nothing. A commit that fails reads the group again: another call's delete that landed first is carried on, as above, and any other write (an unarchive, say) answers `CONFLICT`, having written nothing. **This is the point of no return:** from here unarchive refuses the group ([functions API](functions-api.md#groups)), and a call skips the session, password and group checks and carries on from step 3.
3. Delete the team (one that's gone counts as done). A crash before this leaves the team until a call or the hourly job deletes it; a join or merge meanwhile finds `deletingAt` and leaves the group out ([joining](#joining-a-group), step 2).
4. [Purge](#purging-a-group) the group, ending with `deletingBy`'s member row.

The route works for up to 20 seconds and returns `{ finished }`. A call after step 2 by a caller whose row is `active` (an admin, since someone who left can only be a viewer, or a member or viewer of a group with no joined admin) still passes the membership check once the team is gone: `requireMember()` checks the team only for a `left` row. The purge deletes that row last, so once it has finished a call gets `NOT_A_MEMBER`, which the app treats as done. A caller who moved out has a `left` row, so once step 3 has deleted the team, a later call of theirs gets `NOT_A_MEMBER` straight away, which the app treats as done too, and the [group pass](#finishing-purges) finishes the purge. Afterwards the app opens Groups with "Deleted {name}.", and adds "The rest of it is removed within the hour." when `finished` is false.

### Finishing purges

The `account` hourly job (`account POST /`, scheduled only) runs three passes, in this order, until its time budget is used up:

1. **The account pass** finishes account deletions, the purges of their groups included ([order](#order)).
2. **The group pass** finishes group deletes cut off after step 2: each group with `deletingAt` set (`groups.idx_deletingAt`), skipping those started in the last minute, which the route may still be running. It deletes the team (one that's gone counts as done) and purges the group, ending with `deletingBy`'s member row. If that row is gone, another person's account deletion is purging the group from a row it hadn't kept ([a rerun never decides again](#each-group-they-joined)): its purge deletes that row with the others and ends with its own, which no other purge deletes, so the pass leaves the group to it.
3. **The e2e pass** deletes the accounts the [end-to-end flows](../engineering/testing.md#end-to-end) made, once a run's teardown has labelled them ([#386](https://github.com/rojinc/ledgerly/issues/386)): each Appwrite user labelled `e2e` (`Query.contains('labels', ['e2e'])`), skipping one whose `$updatedAt` is less than a minute old, and one also labelled `deleted`, whose deletion is under way and the account pass's. It deletes a user only when its email also matches `^delivered\+e2e[a-z0-9]{10,}-[a-z0-9-]+@resend\.dev$`, a run's Resend test address, and, before it starts a deletion, its person has at least one identity and every one is an email identity with such an address. Only an API key can set a label, and nobody can read a `resend.dev` inbox. These checks guard against mistakes, such as a real user labelled by accident, not against the e2e key itself: with `users.write` it can already act as any user, including calling `POST /delete` as them, so it's kept as secret as the server's own keys ([secrets](security-and-privacy.md#secrets-inventory)). A labelled user that fails either check is left alone and logged as `e2e_user_not_deleted`, with its user ID only: an error, since only a mistake with the e2e key labels one. For a match, it deletes the account as [`POST /delete`](functions-api.md#account) does once past its checks: [step 2](#order) for the user's person (the one with `deletedAt` set, if any), unless `deletedAt` is already set, then steps 3–7. No refusal applies: the user doesn't sign in, and a run's users all go within the same few runs, so a group they share is kept when the first goes and purged with the last. A user with no person (setup failed before its first sign-in) gets step 7 only, with no identity to check: it deletes only the Appwrite user, which the key can delete itself, and no rows. If Appwrite refuses the label query, the run fails and logs it, rather than finding nobody. A deletion cut off is finished by the account pass on a later run, since `deletedAt` is set.

The account pass goes first, so someone whose account is being deleted while they delete a group settles that purge as part of their own deletion. The e2e pass goes last, and a deletion it cuts off is finished by the account pass on a later run. Of two purges of one group at once (a call and the group pass, or a group delete and the same person's account deletion), one commit fails: each batch of rows gives the group row a fresh `rev`, and a member row the other has deleted fails its delete. The one that fails counts as not finished, not as an error, and logs nothing (no `account_finish_failed`); the next call or run carries on.

## Privacy rules

- Placeholder contact details are server-only. The UI shows other people only their group display name, never their email or phone.
- A placeholder's details go once nothing needs them: 30 days after a removal or a purge took its last member row, [scheduler step 5c](scheduling.md#step-5c-placeholder-clean-up) deletes its identities and the invites sent to them, and replaces its name ([permissions](permissions.md#leaving-a-group)).
- Never write raw emails or phone numbers to logs. Log identity keys hashed, or not at all.
- Collect only what a feature needs. No address book uploads.

More in [Security and privacy](security-and-privacy.md).
